# Understanding Distributed Systems and Partial Failures

## 3. 분산 시스템이란 무엇인가요?

**30–60초 답변**

> 독립적으로 실행되는 컴퓨터나 프로세스가 네트워크로 통신하며 하나의 서비스를 제공하는 시스템입니다. 예를 들어 주문 서버가 자기 DB에 주문을 기록하고 별도의 결제 서버에 승인을 요청합니다. 이때 주문 조회는 정상인데 결제 요청만 지연되거나 끊길 수 있습니다. 이런 부분 실패에서는 주문 서버가 살아 있어도 결제가 실행됐는지 즉시 알기 어렵습니다. 그래서 원격 호출에는 대기 기한을 두고, 요청과 처리 결과를 연결할 식별자를 남기며, 응답이 끊겨도 처리 결과를 확인할 경로를 설계합니다. [Waldo 외, A Note on Distributed Computing](https://www.cs.cmu.edu/~aldrich/papers/classic/note-on-distributed-computing.pdf)

**꼬리 질문 · 주문 서버가 정상인데 시스템 장애라고 할 수 있나요?**

사용자 기능을 기준으로 판단합니다. 주문 내역 `GET`은 정상이어도 결제 `POST`가 지연되면 구매 기능에 부분 장애가 발생한 것입니다. 서비스 평균 성공률과 함께 엔드포인트별 p95·p99, 결제 호출 시간 초과율, 처리 결과 미확인 건수를 봅니다. 동일한 추적 ID로 어느 호출 구간에서 지연과 오류가 생겼는지 좁힙니다.

## 4. 스케일 업과 스케일 아웃의 차이는 무엇인가요?

**30–60초 답변**

> 스케일 업은 한 인스턴스의 CPU나 메모리를 늘리는 방법이고, 스케일 아웃은 인스턴스를 추가해 요청을 나누는 방법입니다. 앱 CPU가 포화되어 있고 같은 요청을 어느 인스턴스에서나 처리할 수 있다면 로드밸런서 뒤에서 앱을 늘리겠습니다. 단일 DB의 메모리나 I/O가 먼저 포화된다면 DB 쿼리를 확인하고, 개선 후에도 자원이 부족할 때 DB 인스턴스 증설을 검토합니다. 스케일 아웃으로 가용성도 높이려면 장애 도메인을 나누고, 대상 하나를 잃은 뒤에도 남은 용량이 피크 트래픽을 처리할 수 있는지 검증하겠습니다. [Microsoft Azure Well-Architected Framework의 확장 전략](https://learn.microsoft.com/en-us/azure/well-architected/reliability/scaling)

**꼬리 질문 · 인스턴스를 두 배로 늘리면 처리량도 두 배가 되나요?**

같은 요청 구성과 유입량으로 부하 테스트를 하며 포화 지점을 비교합니다. 앱 CPU와 대기열이 줄었는데 DB 연결 획득 대기와 잠금 대기가 늘면 병목이 DB로 이동한 것입니다. 증설 전후에 성공 RPS, p99, 오류율, 앱과 DB의 포화 지표를 함께 보고 목표 지연 시간 안에서 처리할 수 있는 최대 유입량을 비교합니다.

## 5. 주문 서버가 보낸 결제 요청에 응답이 없으면 어떻게 하나요?

**30–60초 답변**

> 먼저 주문 ID와 결제 시도 ID, 외부 호출에 사용할 식별자, 금액과 통화를 외부 결제 서비스(PG)에 요청하기 전에 저장하겠습니다. 응답 기한이 지나면 해당 시도를 `UNKNOWN`으로 남기고 사용자에게 확인 중이라고 안내합니다. 이후 결제 상태 조회나 검증된 웹훅으로 같은 시도의 결과를 확인합니다. 성공이면 결제 시도와 주문을 대조해 완료를 한 번만 반영하고, 최종 실패면 실패로 전이합니다. 어느 쪽도 확인되지 않으면 대사 작업에서 다시 확인하겠습니다. 대사 작업은 오래된 미확인 건을 찾아 내부 기록과 외부 거래 기록을 맞춥니다. [Stripe 결제 상태 확인](https://docs.stripe.com/payments/payment-intents/verifying-status)

**꼬리 질문 · 처음 응답이 유실되어 PG 거래 ID가 없으면 어떻게 조회하나요?**

PG가 호출 전에 지정한 가맹점 참조값으로 검색을 지원하는지 확인합니다. 지원한다면 시도에 저장한 참조값으로 찾고, 웹훅에서도 그 값으로 연결합니다. 검색 인덱스의 반영이 지연될 수 있다면 첫 검색에서 결과가 없더라도 시도를 미확인으로 유지합니다. 검색 결과가 지연될 수 있는 계약이라면 빈 결과를 받았을 때도 `UNKNOWN`을 유지합니다. 거래 ID도 참조값 조회 수단도 없다면 PG가 제공하는 거래 내역과 내부 시도를 대조합니다. `UNKNOWN` 건수와 체류 시간, 대사로 확정되기까지 걸린 시간, 확인 기한을 넘긴 건을 측정합니다. [Stripe PaymentIntent 조회](https://docs.stripe.com/api/payment_intents/retrieve) · [Stripe PaymentIntent 검색과 반영 지연](https://docs.stripe.com/api/payment_intents/search)

**꼬리 질문 · 조회 결과와 웹훅이 동시에 도착하면요?**

둘 다 같은 결제 시도를 갱신하도록 하고 현재 상태를 조건으로 갱신합니다. 최종 상태를 확정하는 트랜잭션에서 해당 시도와 연결된 주문에 완료를 한 번만 반영합니다. 중복 이벤트는 이미 적용한 결과를 반환하고, 역순 이벤트가 현재 상태와 충돌하면 PG의 최신 상태를 다시 조회합니다. [Stripe 웹훅의 이벤트 순서와 중복 처리](https://docs.stripe.com/webhooks#event-ordering)

## 6. 타임아웃이 나면 결제 실패라고 판단할 수 있나요?

**30–60초 답변**

> 주문 서버가 알 수 있는 사실은 자기 대기 기한 안에 응답을 받지 못했다는 것입니다. 요청이 결제 서버에 도착하기 전에 끊겼을 수도 있고, 서버가 처리 중일 수도 있으며, 승인 후 응답만 유실됐을 수도 있습니다. 세 경우 모두 주문 서버에서는 같은 타임아웃으로 보입니다. 그래서 호출 지표에는 타임아웃 오류를 남기고, 결제 시도에는 결과 미확인 상태를 남깁니다. 결제 성공이나 실패는 그 시도의 권위 있는 최종 상태를 확인했을 때 반영합니다. [AWS Builders’ Library의 타임아웃과 재시도](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/)

**꼬리 질문 · 요청을 취소하거나 타임아웃을 길게 잡으면 결과가 확실해지나요?**

호출자가 대기를 중단해도 이미 커밋된 원격 작업은 남습니다. 대기 기한은 전체 요청의 응답 목표와 결제 서비스의 지연 분포를 근거로 정합니다. 연결 설정·TLS·응답 대기를 어느 타임아웃이 포함하는지 확인하고, 너무 길게 대기할 때 스레드와 연결을 얼마나 오래 점유하는지도 봅니다. 사용자 응답 기한이 끝난 뒤에는 별도 대사 작업이 정해진 처리 한도 안에서 결과를 확인합니다. [AWS Builders’ Library의 타임아웃과 재시도](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/)

## 7. 결제 결과를 모르는 상태에서 재시도할 때 이중 결제를 어떻게 막나요?

**30–60초 답변**

> 한 번의 결제 시도를 하나의 논리적 작업으로 보고, 첫 전송 전에 멱등 키를 저장해 같은 작업의 모든 재시도에서 재사용하겠습니다. 서버는 호출 주체와 작업 범위 안에서 키에 유일성 제약을 걸고 한 요청만 원자적으로 실행 권한을 얻도록 합니다. 같은 키로 다시 오면 처리 중일 때는 상태 조회 경로를 안내하고, 완료됐다면 저장한 결과를 돌려줍니다. 외부 결제 호출도 PG가 보장하는 범위 안에서 해당 작업에 대응하는 동일한 키를 반복 사용합니다. 그 보장이 없거나 키 보관 기간이 지났으면 기존 시도의 결과를 확인하는 절차로 보냅니다. [AWS Builders’ Library의 멱등 API](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/) · [Stripe 멱등 요청](https://docs.stripe.com/api/idempotent_requests)

**꼬리 질문 · 같은 키가 동시에 들어오거나, 같은 키에 금액이 바뀌어 들어오면요?**

`(호출 주체, 작업 종류, 키)`에 유일성 제약을 두고 시도 레코드를 먼저 커밋합니다. 주문·금액·통화처럼 작업을 결정하는 필드의 비교값을 같이 저장합니다. 삽입 경합에서 진 요청은 기존 레코드를 읽고 값이 다르면 계약에 정한 충돌 응답을 보냅니다. 값이 같으면 저장된 진행 상태나 결과를 반환합니다. 외부 승인 후 내부 결과 저장 전에 중단된 오래된 진행 건은 기존 시도를 조회하고 대사합니다. 이렇게 내부에서 한 번만 완료를 반영하는 보장과 PG가 외부 중복 승인을 차단하는 보장의 범위를 각각 검증합니다. [AWS Builders’ Library의 멱등 API](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

**꼬리 질문 · 새 키가 같은 주문으로 들어오면요?**

키는 같은 논리적 작업의 재전송을 묶는 수단이므로 서로 다른 키만으로는 중복을 식별하기 어렵습니다. 주문당 한 번의 결제 성공을 허용하는 서비스라면 주문에 이미 성공했거나 결과를 확인 중인 결제 시도가 있는지 트랜잭션에서 검사하고 기존 시도 상태를 반환합니다. 기존 시도의 최종 실패를 확인한 뒤 사용자가 별도의 새 결제를 시작하는 경우에는 새 시도와 새 키를 연결합니다.

**꼬리 질문 · 키 보관 기간과 재시도 횟수는 어떻게 정하나요?**

내부 키 보관 기간은 클라이언트 재시도, 지연된 요청의 도착, 미확인 시도의 복구 가능 기간을 고려해 정합니다. 외부 요청의 재전송은 PG의 키 유효 기간과 재시도 가능 오류에 맞춥니다. 요청 경로에서는 한 계층이 재시도를 맡고, 남은 대기 기한과 최대 횟수를 모두 제한합니다. 예를 들어 결제 호출에 600ms를 배정했다면 설정 예시로 250ms 시도를 최대 두 번 허용하고 사이의 대기에는 지수 백오프와 지터를 적용해 최대 100ms 안에서 분산합니다. 실제 수치는 지연 분포와 서비스 계약에 맞춥니다. 재시도 예산이 소진된 결제는 대사 대상으로 넘기고, 원본 대비 추가 호출 비율과 중복 승인 건수를 확인합니다. [Stripe 멱등 키 보관 규칙](https://docs.stripe.com/api/idempotent_requests) · [AWS Builders’ Library의 백오프와 지터](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/)
