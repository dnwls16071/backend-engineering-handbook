# Context Switching and CPU Scheduling

## 14. 컨텍스트 스위칭이란 무엇이며 어떻게 동작하나요?

**30–60초 답변**

> 컨텍스트 스위칭은 CPU가 실행 중이던 스레드를 멈추고 다른 스레드를 이어서 실행하는 과정입니다. 스레드가 I/O를 기다리거나 스케줄러가 현재 스레드를 선점할 때 일어날 수 있습니다. 커널은 나가는 스레드가 나중에 재개할 수 있도록 실행 위치, 스택 포인터, 레지스터 상태를 보존합니다. 다음 스레드를 선택하면 그 스레드의 커널 스택과 실행 상태를 복원하고, 주소 공간이 다르면 메모리 매핑도 전환합니다. 먼저 실행하던 스레드는 선점됐다면 실행 가능 상태로, I/O를 기다린다면 대기 상태로 이동합니다. [OSTEP의 실행 제어와 컨텍스트 스위치](https://pages.cs.wisc.edu/~remzi/OSTEP/cpu-mechanisms.pdf)

**꼬리 질문 · 시스템 콜을 호출하면 항상 컨텍스트 스위칭이 일어나나요?**

시스템 콜은 같은 스레드가 사용자 모드에서 커널 모드로 들어가는 경로입니다. 예를 들어 `read()`가 바로 처리되면 같은 스레드로 돌아옵니다. 읽을 데이터가 없어 호출 스레드가 잠들고 커널이 다른 스레드를 실행하면 그때 컨텍스트 스위치가 일어납니다. 타이머 인터럽트도 커널에 실행권을 돌려주고, 커널은 그 시점에 현재 스레드를 계속 실행할지 결정합니다. [OSTEP의 트랩과 타이머 인터럽트](https://pages.cs.wisc.edu/~remzi/OSTEP/cpu-mechanisms.pdf)

## 15. 컨텍스트 스위칭에는 어떤 비용이 드나요?

**30–60초 답변**

> 직접 비용은 커널이 다음 스레드를 고르고 레지스터를 저장·복원하며, 필요에 따라 주소 공간을 전환하는 데 쓰는 시간입니다. 간접 비용은 전환 뒤에 나타납니다. 다음 스레드의 명령어, 데이터, 주소 변환 정보가 캐시나 TLB에 없으면 다시 채워야 합니다. 다른 코어로 이동하면 코어별 캐시의 이점도 줄어들 수 있습니다. 같은 프로세스의 스레드끼리는 주소 공간을 공유해 주소 공간 전환을 피할 수 있지만, 서로 다른 데이터를 다루면 여전히 캐시 미스가 늘 수 있습니다. 그래서 전환 시간은 CPU, 커널, 작업의 메모리 접근 패턴에 따라 달라집니다. [OSTEP의 멀티프로세서 스케줄링과 캐시 친화성](https://pages.cs.wisc.edu/~remzi/OSTEP/cpu-sched-multi.pdf) · [OSTEP의 TLB와 주소 공간 식별자](https://pages.cs.wisc.edu/~remzi/OSTEP/vm-tlbs.pdf)

**꼬리 질문 · 전환 횟수가 많은 서비스에서 무엇을 확인하나요?**

Linux에서는 `getrusage()`의 자발적·비자발적 전환 횟수와 `/proc/<pid>/schedstat`의 실행 큐 대기 시간을 같은 구간에서 확인합니다. 자발적 전환이 늘면 I/O나 락 대기를, 비자발적 전환과 실행 큐 대기 시간이 함께 늘면 CPU 경합을 우선 확인합니다. 처리량과 p99 지연도 함께 비교해 서비스가 실제로 영향을 받는지 판단합니다. [Linux `getrusage(2)`](https://man7.org/linux/man-pages/man2/getrusage.2.html) · [Linux 스케줄러 통계](https://docs.kernel.org/scheduler/sched-stats.html)

## 16. CPU 스케줄링이란 무엇이며 왜 필요한가요?

**30–60초 답변**

> CPU 스케줄링은 커널이 실행 가능한 스레드 중 어느 것을 어느 CPU에서 언제 실행할지 정하는 일입니다. 여러 스레드가 코어를 공유할 때는 CPU 시간을 배분해야 하고, 실행 중인 스레드가 I/O 때문에 잠들면 다른 스레드에 실행 기회를 줘 CPU를 활용합니다. 선점형 정책은 현재 스레드가 스스로 양보하기 전에도 실행권을 바꿀 수 있습니다. 대화형 작업은 첫 실행까지의 응답 시간을, 배치 작업은 완료 시간과 처리량을, 실시간 작업은 마감 시간 준수를 중요하게 봅니다. 스케줄러는 정책과 작업 특성에 따라 이 목표들에 다른 비중을 둡니다. [OSTEP의 스케줄링 목표와 지표](https://pages.cs.wisc.edu/~remzi/OSTEP/cpu-sched.pdf) · [Linux `sched(7)`의 스케줄링 정책](https://man7.org/linux/man-pages/man7/sched.7.html)

**꼬리 질문 · CPU 사용률과 실행 큐 대기 시간 중 무엇을 보나요?**

둘을 같이 봅니다. CPU 사용률은 CPU가 얼마나 바쁜지, 실행 큐 대기 시간은 실행할 준비를 마친 스레드가 CPU를 얼마나 기다렸는지 보여줍니다. 시스템 전체 CPU 사용률이 낮아도 한 코어에 실행이 집중되면 지연이 커질 수 있습니다. 코어별 사용률과 스레드별 실행 큐 대기 시간을 비교하고, CPU 친화성 설정으로 사용할 수 있는 코어가 제한돼 있는지도 확인합니다. [Linux 스케줄러 통계](https://docs.kernel.org/scheduler/sched-stats.html) · [Linux `sched(7)`의 CPU 친화성](https://man7.org/linux/man-pages/man7/sched.7.html)

## 17. 대표적인 CPU 스케줄링 알고리즘을 비교해 주세요.

**30–60초 답변**

> FCFS는 준비 큐에 들어온 순서대로 실행해서 단순하지만 긴 작업 뒤에 짧은 작업이 몰릴 수 있습니다. SJF는 다음 CPU 실행 구간이 가장 짧은 작업을 먼저 골라 평균 완료 소요 시간을 줄이는 데 유리합니다. 선점형인 SRTF는 남은 실행 시간이 더 짧은 작업이 오면 교체합니다. 두 방식 모두 실행 시간의 추정이 필요합니다. 라운드 로빈은 시간 할당량마다 순서를 돌려 첫 실행 기회를 빠르게 주지만 할당량이 짧을수록 전환 부담이 커집니다. 우선순위 스케줄링은 우선순위가 높은 작업을 먼저 처리하고, MLFQ는 여러 큐 사이에서 작업의 CPU 사용 패턴에 따라 우선순위를 조정합니다. [OSTEP의 FCFS·SJF·SRTF·라운드 로빈](https://pages.cs.wisc.edu/~remzi/OSTEP/cpu-sched.pdf) · [OSTEP의 MLFQ](https://pages.cs.wisc.edu/~remzi/OSTEP/cpu-sched-mlfq.pdf)

**꼬리 질문 · 라운드 로빈의 시간 할당량을 어떻게 정하나요?**

전환으로 소비하는 CPU 시간과 실행 큐의 대기 시간을 함께 봅니다. 단일 코어에서 CPU를 계속 쓰는 같은 우선순위 작업만 있다고 가정하면, 할당량이 길수록 다음 차례까지 더 기다리고 짧을수록 더 자주 전환합니다. Linux의 실시간 `SCHED_RR`은 같은 우선순위의 실행 가능 스레드끼리 순서를 돌리며 실제 할당량은 `sched_rr_get_interval()`로 조회할 수 있습니다. 일반 작업에 적용되는 Linux 스케줄러는 별도의 정책을 따르며, 커널 문서는 6.6부터 공정 스케줄링이 CFS에서 EEVDF로 전환하기 시작했다고 설명합니다. [Linux `sched(7)`](https://man7.org/linux/man-pages/man7/sched.7.html) · [Linux `sched_rr_get_interval(2)`](https://man7.org/linux/man-pages/man2/sched_rr_get_interval.2.html) · [Linux EEVDF 문서](https://docs.kernel.org/scheduler/sched-eevdf.html)

## 18. 스케줄링에서 기아 상태란 무엇이며 어떻게 방지하나요?

**30–60초 답변**

> 기아 상태는 스레드가 실행할 준비를 마쳤는데도 다른 스레드가 계속 선택돼 CPU를 무기한 기다릴 수 있는 상태입니다. 예를 들어 엄격한 우선순위 정책에서 높은 우선순위 작업이 계속 실행 가능하면 낮은 우선순위 작업은 기회를 얻지 못합니다. 에이징은 오래 기다린 작업의 우선순위를 높여 실행 기회를 줍니다. MLFQ에서는 주기적으로 작업의 우선순위를 상향해 낮은 큐에 남은 작업도 실행되게 할 수 있습니다. 운영 중에는 낮은 우선순위 작업의 최대 대기 시간과 실제로 받은 CPU 시간을 확인해 우선순위 설정의 영향을 살핍니다. [OSTEP의 MLFQ 기아 문제와 우선순위 상향](https://pages.cs.wisc.edu/~remzi/OSTEP/cpu-sched-mlfq.pdf) · [Linux 스케줄러 통계](https://docs.kernel.org/scheduler/sched-stats.html)

**꼬리 질문 · 우선순위 역전과는 어떻게 구분하나요?**

우선순위 역전은 높은 우선순위 스레드가 낮은 우선순위 스레드가 가진 락을 기다릴 때 생깁니다. 두 스레드 사이 우선순위의 작업이 락 소유자를 계속 선점하면 대기가 길어집니다. 우선순위 상속을 지원하는 락은 소유자의 우선순위를 일시적으로 높여 락을 빨리 반납할 기회를 줍니다. CPU 스케줄링 기아를 진단할 때는 실행 큐 대기를, 이런 우선순위 역전을 진단할 때는 락 대기와 소유자의 실행 지연을 확인합니다. [Linux RT-mutex의 우선순위 역전과 상속](https://docs.kernel.org/locking/rt-mutex-design.html)
