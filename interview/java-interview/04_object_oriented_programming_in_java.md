# Object-Oriented Programming in Java

## 30. 캡슐화란 무엇이며 왜 중요한가요?

**30–60초 답변**

> 캡슐화는 객체가 상태와 그 상태를 다루는 동작을 함께 관리하고, 호출자에게 필요한 연산만 공개하는 설계입니다. 예를 들어 `Order`가 주문 목록을 직접 공개하면 호출자가 결제 이후에도 항목을 바꿀 수 있습니다. `addItem()`과 `confirm()`을 공개하고 상태 변경을 그 메서드로 모으면, 확정된 주문은 수정할 수 없다는 규칙을 한 곳에서 지킬 수 있습니다. 호출자는 공개된 동작에 의존하므로, 계약을 유지하는 동안 내부 저장 구조를 바꿀 수 있습니다. [JLS §6.6 접근 제어](https://docs.oracle.com/javase/specs/jls/se25/html/jls-6.html#jls-6.6)

**꼬리 질문 · 필드를 모두 `private`으로 선언하면 캡슐화가 되나요?**

`private` 필드라도 getter가 내부의 변경 가능한 목록을 그대로 반환하면 호출자가 그 목록을 바꿀 수 있습니다. 조회 전용 스냅샷이 필요하면 `List.copyOf(items)`로 구조 변경을 막을 수 있습니다. 요소 자체가 변경 가능하면 같은 요소를 참조하므로, 값 객체로 바꾸거나 요소까지 복사할지 결정합니다. [Java `List`의 수정 불가 리스트](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/List.html#unmodifiable)

## 31. Getter와 setter를 무분별하게 만들면 어떤 문제가 생기나요?

**30–60초 답변**

> 필드마다 setter를 열면 어떤 순서와 조건에서 상태를 바꿔야 하는지 여러 호출자가 알아야 합니다. 예를 들어 `setStatus(PAID)`와 `setPaidAt()`을 따로 열어 두면 결제 시각이 없는 완료 주문을 만들 수 있습니다. `markPaid(paidAt)`에서 현재 상태와 시각을 확인하고 관련 필드를 함께 설정하면 상태 전이의 규칙을 객체가 맡습니다. 조회 메서드는 호출자가 필요한 값을 표현하고, 변경 가능한 내부 객체를 반환할 때는 외부 수정이 허용되는지 확인합니다. [JLS §6.6 접근 제어](https://docs.oracle.com/javase/specs/jls/se25/html/jls-6.html#jls-6.6)

**꼬리 질문 · 모든 setter와 getter를 없애야 하나요?**

자료 전달용 DTO나 프레임워크 바인딩 타입에서는 단순 접근자가 계약이 될 수 있습니다. 도메인 객체라면 호출자가 어떤 행위를 하려는지부터 봅니다. 예를 들어 `paidAt()`으로 결제 시각을 읽는 것은 필요한 조회이고, 결제 처리에는 `markPaid()`처럼 상태 전이를 드러내는 이름이 적합합니다.

## 32. 상속이란 무엇이며 언제 사용하나요?

**30–60초 답변**

> 상속은 하위 클래스가 상위 클래스의 상속 가능한 멤버를 이어받고, 오버라이딩할 수 있는 동작을 구체화하는 관계입니다. 상위 타입을 사용하는 코드가 하위 인스턴스를 받아도 기존 계약을 지킬 수 있을 때 사용합니다. 예를 들어 상위 타입의 `read()`가 EOF를 특정 방식으로 표현한다면, 하위 타입은 내부 저장 방식이 달라도 그 규칙을 유지해야 합니다. 상위 클래스가 명시적으로 확장할 지점을 제공하고 하위 타입이 그 전제와 결과를 지킬 수 있는지 확인합니다. [JLS §8.1.4 상위 클래스](https://docs.oracle.com/javase/specs/jls/se25/html/jls-8.html#jls-8.1.4) · [Liskov와 Wing의 행동적 서브타이핑 논문](https://www.cs.cmu.edu/~wing/publications/LiskovWing94.pdf)

**꼬리 질문 · 반환 타입을 바꿔도 오버라이딩인가요?**

반환 타입이 참조 타입이면 하위 메서드가 호환되는 더 구체적인 타입을 반환할 수 있습니다. 예를 들어 부모 메서드가 `Number getValue()`라면 자식 메서드는 `Integer getValue()`로 오버라이딩할 수 있습니다. 메서드 오버라이딩에는 반환 타입 외에도 시그니처, 접근 범위, 검사 예외에 관한 규칙이 적용됩니다. [JLS §8.4.8.3 오버라이딩의 제약](https://docs.oracle.com/javase/specs/jls/se25/html/jls-8.html#jls-8.4.8.3)

## 33. 상속의 단점은 무엇인가요?

**30–60초 답변**

> 하위 클래스가 상위 클래스의 내부 호출 순서나 초기화 방식에 의존하면, 상위 클래스의 변경이 하위 동작을 깨뜨릴 수 있습니다. 예를 들어 상위 클래스 생성자가 오버라이딩된 메서드를 부르면, 그 메서드는 하위 클래스 필드가 초기화되기 전에 실행될 수 있습니다. 상속은 타입 간 결합도도 높입니다. 상위 타입이 약속한 동작을 하위 타입이 지키기 어렵다면, 하위 타입으로 정의하기 전에 관계부터 다시 검토합니다. [JLS §12.5 인스턴스 초기화와 동적 디스패치](https://docs.oracle.com/javase/specs/jls/se25/html/jls-12.html#jls-12.5)

**꼬리 질문 · 확장용 기반 클래스를 설계할 때 무엇을 공개하나요?**

공개 메서드가 언제 확장 메서드를 부르는지, 그 시점에 어떤 상태가 보장되는지 문서화합니다. 생성자에서는 하위 클래스가 오버라이딩할 수 있는 메서드 호출을 피하고, 하위 클래스가 바꾸면 안 되는 흐름은 클래스 내부로 유지합니다. 확장 메서드를 추가할 때는 기존 하위 구현이 받는 입력과 호출 순서를 함께 확인합니다. [JLS §12.5 인스턴스 초기화](https://docs.oracle.com/javase/specs/jls/se25/html/jls-12.html#jls-12.5)

## 34. 상속과 조합의 차이는 무엇인가요?

**30–60초 답변**

> 상속은 하위 객체를 상위 타입으로 사용할 수 있게 만드는 관계입니다. 조합은 객체가 다른 객체를 필드로 가지고 필요한 동작을 위임하는 방식입니다. 예를 들어 `Checkout`이 `DiscountPolicy`를 생성자로 받아 계산을 맡기면, 결제 흐름은 유지하면서 할인 정책을 독립적으로 교체하고 테스트할 수 있습니다. 상위 타입의 계약을 그대로 지키는 특수화가 필요하면 상속을 검토하고, 기존 객체의 일부 동작만 빌리거나 동작을 독립적으로 바꿔야 하면 조합을 검토합니다. [JLS §8.1.4 상위 클래스](https://docs.oracle.com/javase/specs/jls/se25/html/jls-8.html#jls-8.1.4) · [JLS §8.1.5 상위 인터페이스](https://docs.oracle.com/javase/specs/jls/se25/html/jls-8.html#jls-8.1.5)

**꼬리 질문 · 조합만으로 기존 인터페이스를 구현할 수 있나요?**

래퍼가 기존 인터페이스를 직접 구현하고 내부 객체에 호출을 위임할 수 있습니다. 예를 들어 로깅을 추가한 결제 모듈이 `PaymentGateway`를 구현하면 호출자는 동일한 타입으로 사용할 수 있습니다. 래퍼가 오류를 삼키거나 재시도를 추가한다면 기존 계약의 실패 처리와 중복 호출 허용 범위를 확인해야 합니다.

## 35. 다형성이란 무엇이며 왜 필요한가요?

**30–60초 답변**

> 다형성 덕분에 호출자는 공통 타입을 통해 여러 구현을 같은 방식으로 사용할 수 있습니다. 예를 들어 `Notifier`에 `send()`를 선언하고 이메일과 문자 구현을 전달하면, 알림을 보내는 쪽은 어떤 구현인지 확인할 필요 없이 같은 메서드를 호출합니다. 오버라이딩된 인스턴스 메서드를 호출할 때 JVM은 수신 객체의 실제 타입에 맞는 구현을 실행합니다. 기존 호출 코드를 그대로 두고 구현을 추가하려면 새 구현도 공통 타입의 성공과 실패 규칙을 지켜야 합니다. [JLS §15.12.4.4 동적 메서드 탐색](https://docs.oracle.com/javase/specs/jls/se25/html/jls-15.html#jls-15.12.4.4)

**꼬리 질문 · 오버로딩과 오버라이딩은 호출 시 어떻게 선택되나요?**

같은 이름에 매개변수 형태가 여러 개면 컴파일러가 인자의 정적 타입 등을 기준으로 호출할 시그니처를 고릅니다. 이후 그 시그니처가 오버라이딩 가능한 인스턴스 메서드라면 런타임에 수신 객체의 타입에 맞는 구현이 선택됩니다. 예를 들어 `Object value = "hello"`를 `print(Object)`와 `print(String)`에 넘길 때 오버로드 선택은 `Object`를 기준으로 합니다. [JLS §15.12.2 오버로드 결정](https://docs.oracle.com/javase/specs/jls/se25/html/jls-15.html#jls-15.12.2) · [JLS §15.12.4.4 동적 메서드 탐색](https://docs.oracle.com/javase/specs/jls/se25/html/jls-15.html#jls-15.12.4.4)

## 36. `instanceof`를 사용하면 어떤 문제가 생길 수 있나요?

**30–60초 답변**

> 객체가 직접 처리할 수 있는 행동을 호출자마다 `instanceof`로 분기하면 새 타입이 늘 때마다 여러 위치를 수정해야 합니다. 예를 들어 상품별 할인 계산을 다양한 서비스에서 타입 검사로 반복하면 특정 서비스의 분기를 빠뜨릴 수 있습니다. 각 타입의 책임으로 자연스럽게 넣을 수 있는 동작이라면 공통 메서드나 정책 객체를 사용해 그 구현에 맡깁니다. 외부에서 온 `Object`의 타입을 확인하거나, 닫힌 타입 집합을 한 곳에서 변환하는 경우에는 타입 검사가 적합할 수 있습니다. [JLS §15.20.2 `instanceof`](https://docs.oracle.com/javase/specs/jls/se25/html/jls-15.html#jls-15.20.2) · [Java 21의 패턴 `switch`](https://docs.oracle.com/en/java/javase/21/language/pattern-matching-switch.html)

**꼬리 질문 · 패턴 매칭을 쓰면 새 타입을 빠뜨리는 문제도 해결되나요?**

`obj instanceof String text`는 검사와 변수 바인딩을 함께 제공합니다. 새 타입을 확인할 분기를 자동으로 추가하지는 않습니다. Java 21의 패턴 `switch` 표현식에서 `sealed` 타입의 허용 하위 타입을 모두 다루고 포괄 분기를 생략하면, 새 허용 타입을 추가한 뒤 호출 코드도 재컴파일할 때 누락된 분기를 컴파일러가 찾을 수 있습니다. [JLS §15.20.2 `instanceof`](https://docs.oracle.com/javase/specs/jls/se25/html/jls-15.html#jls-15.20.2) · [Java 21 패턴 `switch`의 완전성 검사](https://docs.oracle.com/en/java/javase/21/language/pattern-matching-switch.html)

## 37. 인터페이스와 추상 클래스는 어떻게 다른가요?

**30–60초 답변**

> 인터페이스는 서로 다른 클래스가 공유할 수 있는 타입 계약입니다. 클래스는 여러 인터페이스를 구현할 수 있고, 인터페이스는 `default` 메서드로 공통 구현을 제공할 수 있습니다. 인터페이스가 선언하는 필드는 `public static final`이고 클래스 인스턴스마다 따로 보관할 필드는 선언할 수 없습니다. 추상 클래스는 인스턴스 필드, 생성자, 접근 범위가 다른 메서드를 가질 수 있어 공통 상태와 초기화 규칙을 함께 관리하는 데 적합합니다. Java 클래스가 직접 상속할 수 있는 클래스는 하나입니다. [JLS §8 클래스](https://docs.oracle.com/javase/specs/jls/se25/html/jls-8.html) · [JLS §9 인터페이스](https://docs.oracle.com/javase/specs/jls/se25/html/jls-9.html)

**꼬리 질문 · 서로 독립적인 두 인터페이스가 같은 `default` 메서드를 제공하면요?**

두 기본 구현이 모두 상속 대상이면 클래스가 메서드를 오버라이딩해 충돌을 해소합니다. 직접 구현하는 인터페이스라면 규칙에 따라 `InterfaceName.super.method()`로 그 구현을 호출할 수 있습니다. 상위 클래스에서 같은 시그니처의 구체적인 인스턴스 메서드를 상속하는 경우에는 클래스 쪽 메서드가 우선합니다. [JLS §8.4.8.4 같은 시그니처를 가진 메서드의 상속](https://docs.oracle.com/javase/specs/jls/se25/html/jls-8.html#jls-8.4.8.4)

## 38. 언제 인터페이스를 쓰고, 언제 추상 클래스를 쓰나요?

**30–60초 답변**

> 이메일과 문자처럼 구현 방식과 상태는 다르지만 호출자가 하나의 역할로 다뤄야 할 때는 `Notifier` 같은 인터페이스를 사용합니다. 밀접하게 관련된 타입이 같은 상태와 검증 절차를 공유해야 한다면 추상 클래스를 검토합니다. 예를 들어 파일 처리 순서와 오류 처리 규칙은 공통으로 고정하고, 형식별 파싱 단계만 하위 클래스에 열 수 있습니다. 호출자는 인터페이스를 사용하고, 공통 구현이 필요한 일부 구현체만 추상 클래스를 상속하는 방식도 가능합니다. [JLS §8.1 클래스 선언](https://docs.oracle.com/javase/specs/jls/se25/html/jls-8.html#jls-8.1) · [JLS §9.1 인터페이스 선언](https://docs.oracle.com/javase/specs/jls/se25/html/jls-9.html#jls-9.1)

**꼬리 질문 · 공통 로직이 생기면 기본 메서드로 올려도 되나요?**

기존 인터페이스 연산만으로 표현할 수 있고 모든 구현에서 같은 의미를 가진 동작이면 `default` 메서드를 검토합니다. 구현체마다 필요한 상태나 의존성이 다르면 별도 객체로 공통 로직을 위임할 수 있습니다. 이미 쓰이는 인터페이스에 기본 메서드를 추가할 때는 다른 인터페이스와 함께 구현한 클래스에서 같은 시그니처가 충돌하는지 확인합니다. [JLS §9.4 인터페이스 메서드](https://docs.oracle.com/javase/specs/jls/se25/html/jls-9.html#jls-9.4)
