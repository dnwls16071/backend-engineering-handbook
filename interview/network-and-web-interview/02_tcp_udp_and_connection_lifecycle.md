# TCP, UDP, and Connection Lifecycle

## 1. TCP의 장점과 단점은 무엇인가요?

**30–60초 답변**

> TCP는 연결을 맺고 애플리케이션에 신뢰성 있는 순서 보장 바이트 스트림을 제공합니다. 손실된 데이터를 재전송하고 중복 데이터를 제거하며, 수신 측과 네트워크 상황에 맞춰 전송량을 제한합니다. 그래서 파일처럼 바이트가 빠짐없이 순서대로 도착해야 하는 데이터를 전송하기 편합니다. 새 연결을 맺는 데 왕복 시간이 들고, 양쪽이 연결 상태와 버퍼를 유지해야 합니다. 또 앞부분에 손실이 생기면 뒤의 바이트가 먼저 도착해도 빠진 부분이 복구될 때까지 순서대로 읽을 수 있는 범위가 늘지 않습니다. [RFC 9293 TCP](https://www.rfc-editor.org/rfc/rfc9293) · [RFC 5681 TCP 혼잡 제어](https://www.rfc-editor.org/rfc/rfc5681)

**꼬리 질문 · 송신 측에서 `write()`를 두 번 호출하면 수신 측 `read()`도 각각 한 번씩 돌려주나요?**

TCP는 바이트의 순서를 보장하고 쓰기 호출의 경계는 보존하지 않습니다. 수신 측은 두 쓰기의 데이터를 한 번에 읽거나 한 쓰기의 데이터를 여러 번에 나눠 읽을 수 있습니다. 애플리케이션 프로토콜에서 길이 헤더나 구분자로 메시지 경계를 정하고, 수신 버퍼에 모아 완전한 메시지를 꺼냅니다. [RFC 9293 TCP](https://www.rfc-editor.org/rfc/rfc9293)

## 2. UDP는 TCP와 어떻게 다른가요?

**30–60초 답변**

> UDP는 전송 계층 핸드셰이크 없이 개별 데이터그램을 보내고, 수신 측에서 데이터그램 경계를 유지합니다. UDP 자체에서 전달 성공, 순서, 중복 제거, 재전송을 보장하지 않으므로 애플리케이션이 필요한 기능을 선택합니다. 작은 요청과 응답을 주고받을 때는 연결 설정 비용을 줄일 수 있고, 실시간 음성에서는 늦게 재전송된 데이터보다 재생 시점에 맞춰 도착한 데이터가 더 유용할 수 있습니다. TCP는 신뢰성 있는 순서 보장 바이트 스트림에 흐름 제어와 혼잡 제어를 제공합니다. UDP 위에서도 QUIC처럼 스트림 단위의 신뢰성, 흐름 제어, 혼잡 제어를 갖춘 프로토콜을 구현할 수 있습니다. [RFC 768 UDP](https://www.rfc-editor.org/rfc/rfc768) · [RFC 8085 UDP 사용 가이드](https://www.rfc-editor.org/rfc/rfc8085) · [RFC 9293 TCP](https://www.rfc-editor.org/rfc/rfc9293) · [RFC 9000 QUIC](https://www.rfc-editor.org/rfc/rfc9000)

**꼬리 질문 · 실시간 음성 서비스를 UDP로 만들 때 손실이 늘면 어떻게 대응하나요?**

패킷 번호와 타임스탬프로 손실과 지연을 구분하고, 재생 기한이 지난 패킷은 건너뜁니다. 수신 보고에서 손실과 지연 변화를 보며 필요하면 인코딩 비트레이트를 낮춥니다. 종단 간 지연과 음성 끊김을 함께 측정해 수신 버퍼와 전송량을 조정합니다. [RFC 8085 UDP 사용 가이드](https://www.rfc-editor.org/rfc/rfc8085) · [RFC 3550 RTP와 수신 보고](https://www.rfc-editor.org/rfc/rfc3550)

## 3. TCP의 3-way handshake와 4-way handshake를 설명해 주세요.

**30–60초 답변**

> 일반적인 연결 수립에서 클라이언트가 `SYN`으로 초기 순서 번호를 보내고, 서버는 이를 확인하면서 자신의 초기 순서 번호를 담은 `SYN+ACK`을 보냅니다. 클라이언트가 마지막 `ACK`을 보내면 양쪽 순서 번호의 교환과 확인이 끝납니다. 정상 종료에서는 한쪽이 `FIN`으로 자기 송신이 끝났음을 알리고 상대가 `ACK`으로 확인하므로, 상대는 자기 송신 방향으로 남은 데이터를 계속 보낼 수 있습니다. 상대도 보내기를 마치면 자기 `FIN`을 보내고 처음 닫은 쪽이 `ACK`을 보내며, 상황에 따라 두 번째와 세 번째 단계의 `ACK`과 `FIN`을 한 세그먼트로 보낼 수도 있습니다. 전형적인 순차 종료에서 먼저 `FIN`을 보낸 쪽은 `TIME_WAIT`에서 지연된 세그먼트가 사라지기를 기다리고, 마지막 `ACK`이 유실돼 상대가 `FIN`을 재전송하면 다시 확인 응답을 보냅니다. [RFC 9293 TCP 연결 수립과 종료](https://www.rfc-editor.org/rfc/rfc9293)

**꼬리 질문 · 서버에서도 `TIME_WAIT`가 많이 생길 수 있나요?**

서버가 먼저 연결을 닫는 경우 서버 쪽에 `TIME_WAIT`가 생길 수 있으며, 양쪽이 동시에 종료를 시작하면 양쪽이 이 상태에 들어갈 수 있습니다. 표준의 대기 기준은 최대 세그먼트 수명(MSL)의 두 배입니다. 서버에서 이 상태가 급증했다면 먼저 누가 `FIN`을 시작하는지, 연결 재사용률이 떨어졌는지, 연결 실패도 함께 늘었는지 확인합니다. [RFC 9293 TCP 상태 전이와 종료](https://www.rfc-editor.org/rfc/rfc9293)

## 4. TCP는 신뢰성을 어떻게 보장하고, 흐름 제어와 혼잡 제어는 어떻게 다른가요?

**30–60초 답변**

> TCP는 체크섬으로 손상된 세그먼트를 검사하고, 순서 번호와 누적 `ACK`으로 연속해서 받은 바이트 범위를 확인합니다. 송신 측은 재전송 타이머나 중복 `ACK` 같은 신호로 손실을 감지해 다시 보내고, 수신 측은 중복을 제거해 바이트를 순서대로 넘깁니다. 흐름 제어는 수신 측이 광고한 수신 윈도우 `rwnd`로 수신 버퍼를 보호합니다. 혼잡 제어는 송신 측이 손실 등의 신호에 따라 혼잡 윈도우 `cwnd`를 조절해 네트워크 부하를 제어합니다. 따라서 송신 측이 아직 확인받지 않고 전송할 수 있는 데이터의 양은 두 윈도우 중 작은 값의 제한을 받습니다. [RFC 9293 TCP](https://www.rfc-editor.org/rfc/rfc9293) · [RFC 5681 TCP 혼잡 제어](https://www.rfc-editor.org/rfc/rfc5681)

**꼬리 질문 · TCP `ACK`을 받으면 상대 애플리케이션 처리까지 끝났다고 봐도 되나요?**

TCP `ACK`은 상대의 TCP 계층이 바이트를 받았다는 뜻입니다. 상대 애플리케이션에서의 읽기, 요청 처리, DB 커밋 결과는 HTTP 응답이나 작업 상태 조회처럼 애플리케이션 수준에서 정한 신호로 확인합니다. [RFC 9293 TCP](https://www.rfc-editor.org/rfc/rfc9293)

## 5. TCP/IP 4계층과 OSI 7계층을 비교해 주세요.

**30–60초 답변**

> OSI는 통신 기능을 물리, 데이터 링크, 네트워크, 전송, 세션, 표현, 응용의 7계층으로 나눈 참조 모델입니다. 인터넷 프로토콜을 설명하는 TCP/IP 모델은 링크, 인터넷, 전송, 응용의 4계층으로 정리할 수 있습니다. 물리·데이터 링크 기능은 TCP/IP의 링크 쪽에, 네트워크는 인터넷 계층에, 전송은 전송 계층에 대략 대응합니다. OSI의 세션·표현·응용 기능은 TCP/IP 프로토콜을 설명할 때 전송 위에서 함께 다루는 경우가 많고, 실제 기능 배치는 프로토콜에 따라 달라집니다. 웹 요청을 예로 들면 HTTP는 응용, TCP는 전송, IP는 인터넷, Ethernet은 링크에 해당합니다. [ITU-T X.200 OSI 참조 모델](https://www.itu.int/rec/T-REC-X.200-199407-I/en) · [RFC 1122 인터넷 호스트의 계층](https://www.rfc-editor.org/rfc/rfc1122)

**꼬리 질문 · 연결은 성공했는데 응답이 `500`이면 어느 계층부터 확인하나요?**

HTTP `500`은 응답을 보낸 서버가 요청을 처리하는 중 예상하지 못한 오류를 만났다는 응용 계층 신호입니다. 요청 ID로 프록시와 애플리케이션 로그를 대조하고, 응답을 실제로 생성한 구성 요소와 관련 하위 호출을 확인합니다. TCP와 TLS 연결이 성공했다는 사실은 그 응답을 보낸 지점까지 통신할 수 있었다는 근거로 씁니다. [RFC 9110 HTTP 500](https://www.rfc-editor.org/rfc/rfc9110#section-15.6.1)
