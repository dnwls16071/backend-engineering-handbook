# Designing Application Ports for Member Authentication

포트는 외부와 애플리케이션 사이에 오가는 목적 있는 계약이다. 회원 인증을 예로 들면 입력 포트는 “제출한 자격 증명으로 회원을 인증한다”라는 업무 요청을 표현한다. HTTP, CLI, 테스트처럼 호출 방식이 바뀌어도 애플리케이션 계약은 같은 의미를 유지할 수 있다. [Alistair Cockburn · Hexagonal Architecture](https://alistair.cockburn.us/hexagonal-architecture)

## 1. 포트의 목적과 소유권

| 경계 | 계약 예 | 소유권과 이유 |
| --- | --- | --- |
| 입력 포트 | `AuthenticateMember` | 애플리케이션이 인증에 필요한 입력, 성공 결과와 실패 의미를 정한다. |
| 출력 포트 | `LoadMemberCredentials` | 애플리케이션이 검증에 필요한 최소 조회 형태를 정의한다. |
| 출력 포트 | `VerifyPassword` | 애플리케이션이 비밀번호 일치 여부를 요청하고 어댑터가 검증 기술을 적용한다. |
| 입력 어댑터 | 웹 로그인, Spring Security 연결, 테스트 | 외부 입력을 인증 계약으로 바꾸고 응답을 해당 환경에 맞춰 전달한다. |

입력과 출력의 이름은 애플리케이션을 기준으로 정한다. 클래스 하나마다 인터페이스를 늘리기보다, 호출자가 오해하기 쉬운 의미나 교체해야 하는 외부 능력을 계약으로 드러낸다. 내부 헬퍼는 모듈에서 함께 변경할 수 있다.

## 2. 인증 정책과 기술의 경계

인증 서비스는 자격 증명 확인과 계정 상태에 따른 정책을 조합한다. 비밀번호 검증 어댑터는 검증된 라이브러리와 적응형 단방향 해시를 사용한다. 원문 비밀번호는 필요한 호출 범위에서만 다루고 로그나 결과 객체에 남기지 않는다. 성공한 포트 응답은 회원 식별자와 유스케이스가 약속한 인증 결과를 담는다. 세션 쿠키와 HTTP 표현은 웹 또는 보안 어댑터에서 다룬다. 세션 발급이 업무 흐름의 일부라면 별도의 능력으로 모델링할 수 있다. [Spring Security · Password Storage](https://docs.spring.io/spring-security/reference/features/authentication/password-storage.html)

인증은 호출자의 신원을 확인한다. 인가는 그 신원으로 특정 작업을 할 수 있는지 판단한다. 예를 들어 로그인한 회원도 승인된 강사만 호출할 수 있는 유스케이스에서는 접근이 거절될 수 있다. 로그인 실패 응답은 외부에서 계정 존재 여부나 상태를 쉽게 알아낼 수 없도록 일관된 계약으로 정한다. 내부 진단에 필요한 실패 이유와 외부 응답은 접근 목적이 다른 정보로 다룬다. [OWASP Authentication Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)

## 3. 개발 가이드에 남길 계약

- 어떤 호출자가 포트를 사용하고 어떤 업무를 수행하는가.
- 인증에 필요한 최소 입력과 성공 결과는 무엇인가.
- 실패 결과 중 외부 공개가 허용되는 범위는 어디까지인가.
- 자격 증명 검증과 계정 정책은 각각 어느 테스트에서 확인하는가.
- 새 인증 제공자를 연결할 때 교체할 어댑터와 유지해야 할 계약은 무엇인가.

새 로그인 진입점을 추가할 때도 이 계약을 기준으로 비교한다. 인증 포트 설명에 특정 HTTP 헤더나 저장소의 조회 타입이 계속 등장한다면 어댑터에서 변환할 수 있는지 살펴본다.
