# Active Code Reading and Pragmatic Design

코드를 읽을 때는 동작에 대한 가설을 세우고, 사례와 테스트로 확인한다. 설계를 바꿀 때도 같은 방식으로 접근한다. 지금 겪는 문제를 명시하고, 선택한 변경이 그 문제를 실제로 줄이는지 확인한다.

## 1. 능동적으로 읽기

기술 문서나 코드 리뷰에서 접한 조언은 적용 조건을 생각하면서 읽는다. 무엇을 개선하는 조언인지, 어떤 상황에서 효과가 있는지 적어 두고, 익숙한 코드의 작은 사례에 적용해 본다. 실행 결과가 예상과 다르면 코드와 자신의 해석을 함께 다시 살펴본다.

코드에서는 호출부나 공개 메서드에서 시작해 한 가지 질문을 따라간다. 앞 장의 주문 포장 예제를 읽는다면 “총무게가 정확히 2,000g일 때 어떤 박스를 선택하는가?”에서 시작할 수 있다. [주문 포장 리팩터링 실습](05_refactoring_for_abstraction_and_cohesion.md)

| 읽는 단계 | 주문 포장 예제에서 확인하는 내용 |
| --- | --- |
| 동작 예측 | 2,000g은 기준에 포함되므로 `SMALL`일 것으로 예상한다. |
| 판단 위치 찾기 | `Packing.prepare`에서 포장 정책으로 내려가 `BoxPolicy.selectFor`의 비교식을 확인한다. |
| 예시로 검증 | 1,999g, 2,000g, 2,001g의 예상 결과를 실행 결과와 대조한다. |
| 의도 기록 | “2,000g까지 허용”이 요구사항인지 확인한다. 이유를 알 수 없으면 질문으로 남긴다. |

코드와 테스트는 구현된 동작의 근거다. 업무 규칙의 이유나 아직 합의되지 않은 조건은 결정 기록이나 담당자에게 확인한다.

## 2. 오버 엔지니어링 판단하기

향후 요구를 예상해 확장점을 추가하면 구현뿐 아니라 테스트, 설정, 변경할 때 검토할 범위도 늘어난다. 추가할 구조가 현재의 어떤 변경을 단순하게 만드는지 설명할 수 있는지 확인한다.

모든 창고가 같은 박스 기준을 쓰고 기준 변경도 드물다면 하나의 `BoxPolicy`로 표현할 수 있다. 창고마다 허용 무게나 박스 종류가 실제로 달라지면, 달라지는 값과 계산을 확인한 뒤 창고별 설정이나 교체 가능한 정책 중 맞는 구조를 고른다. 현재 계약을 검증하는 테스트가 있으면 그때 동작을 확인하면서 구조를 바꿀 수 있다.

YAGNI는 장래에 필요할 것으로 예상한 기능이나 확장점을 실제 요구가 생길 때 검토하자는 원칙이다. 현재 동작을 읽기 쉽게 정리하거나 검증을 쉽게 만드는 작업은 이후 변경 비용을 줄이는 데 도움이 된다. [Martin Fowler의 YAGNI](https://martinfowler.com/bliki/Yagni.html)

## 3. 한 가지 기법이 해결하는 범위 보기

프레더릭 브룩스는 *No Silver Bullet*에서 소프트웨어의 어려움을 문제 자체와 구현 과정에서 생기는 어려움으로 나눠 살폈다. 당시 그는 기술이나 관리 기법 하나만으로 생산성, 신뢰성, 단순성이 단기간에 크게 개선되기를 기대하기 어렵다고 보았다. [Frederick P. Brooks Jr.의 No Silver Bullet](https://www.cs.unc.edu/techreports/86-020.pdf)

| 어려움 | 주문 포장 예제에서 보이는 모습 |
| --- | --- |
| 문제 자체의 복잡성 | 주문을 분할해서 보낼 수 있는지, 포장재 무게를 포함하는지, 무게 상한을 어느 시점 기준으로 적용하는지 정해야 한다. |
| 구현 과정의 복잡성 | 중복된 단위 변환, 찾아가기 어려운 분기, 손으로 반복하는 검증 때문에 변경 시간이 늘어난다. |

값 객체로 단위를 명시하고 경계 사례를 테스트하면 구현에서 생기는 실수를 줄일 수 있다. 분할 출고나 포장재 무게 같은 정책은 업무 관계자와 정하고, 실제 사례로 검증한다. 설계 패턴을 적용할 때도 해결하려는 문제가 무엇인지부터 확인한다. [객체 지향 설계와 SOLID](02_object_oriented_design_and_solid_principles.md)
