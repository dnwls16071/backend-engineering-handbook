# AGENTS.md: 프로젝트 맥락과 작업 규칙을 지속적으로 전달하기

## 1. 반복해서 설명하던 규칙을 프로젝트에 남긴다

- **`AGENTS.md`는 Codex가 작업 전에 읽는 프로젝트 지침 파일이다.**
- 프로젝트 구조, 팀 관례, 테스트 절차, 보안 제약과 아키텍처 패턴을 전달한다.
- 매번 대화에서 같은 규칙을 설명하는 대신 팀 지식을 재사용할 수 있는 형태로 남긴다.
- 프로젝트 맥락이 부족하면 잘못된 디렉터리 수정, 테스트 생략, 아키텍처 위반, 오래된 API 사용 같은 실수가 발생하기 쉽다.
- 명확한 지침은 에이전트가 관례를 추측하는 일을 줄이고 작업의 일관성을 높이는 데 도움이 된다.

## 2. 실제 작업에 필요한 정보를 구체적으로 작성한다

| 항목 | 기록할 내용 |
| :--- | :--- |
| 프로젝트 구조 | 주요 모듈, 서비스 배치와 디렉터리별 역할 |
| 실행 명령 | 의존성 설치, 개발 서버 실행, 빌드, 테스트와 린트 명령 |
| 구현 규칙 | 명명 관례, 코딩 스타일과 아키텍처 패턴 |
| 작업 제약 | 수정하면 안 되는 경로와 보안 정책 |
| 검증 절차 | PR 제출 전 실행할 테스트와 확인 사항 |

- **추상적인 권고보다 실제 명령과 구체적인 제약을 적는다.**
- 예를 들어 “테스트를 잘 실행한다”보다 실행할 명령과 시점을 명시한다.
- 다음은 설치·실행 방법, 스타일과 변경 제약을 담은 예시이다.

```markdown
## Setup

- pnpm install
- pnpm test
- pnpm dev

## Style

- TypeScript strict mode를 사용한다.
- 문자열에는 작은따옴표를 사용한다.
- 함수형 패턴을 우선한다.

## Safety

- /vendor 디렉터리를 수정하지 않는다.
- PR 제출 전에 테스트를 실행한다.
```

## 3. 개인·저장소·서비스 지침을 계층으로 나눈다

- 하나의 큰 문서에 모든 규칙을 넣는 대신 적용 범위에 따라 여러 `AGENTS.md`를 둘 수 있다.

| 위치 | 적용 목적 |
| :--- | :--- |
| `~/.codex/AGENTS.md` | 개인의 기본 스타일, 작업 방식과 선호 사항 |
| `repo/AGENTS.md` | 저장소 전체에 공통으로 적용할 규칙 |
| `repo/services/payment/AGENTS.md` | 특정 서비스의 구현·검증 규칙 |

```text
repo/
├── AGENTS.md
└── payments/
    └── AGENTS.md
```

- `payments` 안에서 작업하면 저장소 공통 지침과 해당 디렉터리의 지침을 함께 적용한다.
- **지침이 충돌하면 작업 대상에 더 가까운 디렉터리의 지침이 우선한다.**
- 공통 규칙은 상위에 두고 서비스별 차이만 하위에 기록하면 중복을 줄일 수 있다.
- `AGENTS.override.md`를 활용하면 특정 영역에 별도의 지침을 적용할 수 있다.
- 민감한 서비스에 더 엄격한 로컬 정책이 필요할 때도 적용 범위를 나누어 관리한다.

## 4. 모노레포에서는 서비스별 작업 방식을 구분한다

```text
repo/
├── AGENTS.md
├── frontend/
│   └── AGENTS.md
├── backend/
│   └── AGENTS.md
├── infra/
│   └── AGENTS.md
└── payments/
    └── AGENTS.md
```

- 프런트엔드, 백엔드, 인프라와 결제 서비스는 서로 다른 구현 규칙과 검증 절차를 가질 수 있다.
- 저장소 공통 지침에는 팀 전체의 규칙을 두고, 서비스별 지침에는 해당 영역에 필요한 내용만 작성한다.
- 서비스마다 독립적인 작업 흐름과 보안 요구사항을 전달할 수 있다.
- 지침을 나누는 것만으로 실제 접근 권한이나 보안 경계가 만들어지는 것은 아니다.

## 5. 지침과 실행 권한 제어를 함께 사용한다

- **`AGENTS.md`는 행동을 안내하는 수단이며, 규칙 준수를 강제하는 보안 장치는 아니다.**
- 지침이 있어도 에이전트는 실수하거나 규칙을 놓칠 수 있다.
- 실제 실행 범위는 샌드박스, 승인 시스템, 권한 제어와 실행 정책으로 관리한다.
- 운영 배포, 데이터베이스 작업과 자격 증명 관리에서는 문서에 적힌 주의사항만으로 권한을 통제하지 않는다.
- 프로젝트 맥락을 전달하는 일과 시스템 차원에서 실행을 제한하는 일을 함께 설계한다.

## 6. AGENTS.md와 Skills의 역할을 구분한다

| 구분 | 역할 | 담을 내용의 예시 |
| :--- | :--- | :--- |
| `AGENTS.md` | 작업 전반에 적용할 지속적인 맥락과 규칙 | 프로젝트 구조, 코딩 관례와 기본 검증 명령 |
| Skills | 특정 작업에서 재사용할 절차 | 릴리스, PR 리뷰와 마이그레이션 흐름 |

- `AGENTS.md`에는 프로젝트에서 계속 알아야 할 내용을 남긴다.
- 특정 작업에만 필요한 반복 절차는 Skills로 분리해 재사용한다.

## 7. 짧고 구체적으로 유지하고 변경을 검토한다

- **핵심 지침을 짧게 유지한다.** 지나치게 큰 문서보다 작업에 필요한 규칙을 우선한다.
- **실제 팀 규칙을 적는다.** 일반적인 조언보다 프로젝트에서 쓰는 명령과 제약을 기록한다.
- **버전 관리에 포함한다.** 규칙 변경도 PR을 통해 검토한다.
- **서비스별 차이는 로컬 지침으로 나눈다.** 공통 규칙의 중복을 줄인다.
- 좋은 맥락은 불필요한 탐색과 반복 설명을 줄여 실행 시간, 토큰 사용량과 결과의 일관성을 개선하는 데 도움이 된다.

## 8. 프롬프트 표현보다 맥락의 품질을 높인다

- 좋은 결과에는 명확한 제약, 아키텍처 맥락과 운영 지식이 필요하다.
- 프롬프트를 길게 쓰거나 표현을 다듬는 것만으로 프로젝트 지식을 대신할 수 없다.
- `AGENTS.md`와 같은 맥락 파일은 여러 에이전트 생태계에서 공통 작업 방식을 전달하는 방향으로 확산되고 있다.
- **에이전트가 어떤 맥락을 읽고 어떤 범위에서 판단해야 하는지 설계하는 일도 엔지니어링의 일부이다.**
