# Test Fixtures and State Isolation

픽스처는 테스트에 필요한 시스템 상태, 요청 데이터, 클라이언트를 일관된 방식으로 준비한다. 좋은 픽스처를 사용하면 테스트 본문에서 사전 조건과 기대 결과를 한눈에 읽을 수 있다.

## 1. 테스트 문맥을 드러내는 픽스처

테스트 메서드가 읽기의 출발점이 되도록 한다. 인증된 사용자가 필요하면 `fixture.asSeller(seller)`처럼 누가 요청하는지 표현하고, 중복이 필요한 테스트라면 `fixture.existingAccount(email)`처럼 어떤 상태를 만들었는지 적는다. 식별자가 결과 검증에 필요한 경우에는 준비 동작에서 반환받아 변수에 둔다.

- 픽스처는 회원 데이터 생성, 인증 요청, JSON 조립처럼 반복되는 절차를 묶는다. 시나리오에 중요한 계정, 역할, 상태는 호출 인자나 변수에 남긴다.
- 테스트 DSL은 자주 쓰는 준비와 호출에 도메인 이름을 붙인다. 순서에 따라 클라이언트의 기본 인증 상태를 바꾸는 호출은 이후 테스트가 따라야 할 숨은 전제도 만들 수 있다. 인증 상태가 독립적인 클라이언트를 반환하면 영향을 추적하기 쉽다.
- 준비 단계의 요청은 응답 코드와 예상한 결과를 즉시 확인한다. 준비 실패가 뒤늦은 `NullPointerException`으로 드러나면, 본검사가 깨졌는지 준비가 실패했는지 구분하기 어렵다.
- `@BeforeEach`는 각 테스트 실행 전에 동작한다. 모든 테스트에 필요한 기계적인 준비에는 적합하고, 시나리오마다 다른 전제는 테스트 본문이나 본문에서 호출한 픽스처에 둔다. `@BeforeAll`로 준비한 가변 상태는 테스트 간에 공유되는지 점검한다.

**공식 문서** [JUnit 테스트 생명주기](https://docs.junit.org/5.14.4/writing-tests/test-instance-lifecycle.html)

## 2. 유효한 기본값과 통제된 테스트 데이터

| 상황 | 데이터 준비 방식 |
| --- | --- |
| 정상 경로 | 모든 필드가 현재 정책을 만족하는 기본 데이터를 만든다. |
| 단일 규칙 위반 | 유효한 기본 데이터에서 이번에 검증하는 속성만 바꾼다. 예를 들어 주소가 비어 있는 경우 다른 필드는 유효하게 둔다. |
| 유일성 | 이메일과 키는 테스트마다 구분하고, 중복 검증에서만 같은 값을 의도적으로 재사용한다. |
| 값의 경계 | 최소 길이 바로 아래와 최소 길이, 만료 시각 직전과 직후처럼 의미 있는 값을 명시한다. |
| 생성 데이터 변동 | 입력 공간을 넓히기 위해 무작위 값을 쓴다면 실패 입력이나 시드를 남겨 재현할 수 있게 한다. 현재 정책을 위반하는 값이 기본값으로 생성되지 않는지 확인한다. |

매개변수화 테스트 데이터가 여러 곳에 반복된다면 `@MethodSource`를 재사용할 수 있다. 여러 시나리오가 같은 유효성 규칙을 공유할 때만 데이터 소스나 합성 애노테이션으로 일반화한다. 테스트 요구사항이 검색 한도나 시간 경계처럼 특정 값에 달려 있다면 테스트에서 직접 드러내는 편이 읽기 쉽다.

**공식 문서** [JUnit 테스트 데이터 소스](https://docs.junit.org/5.14.4/writing-tests/parameterized-classes-and-tests.html#tests-sources)

## 3. 격리할 상태의 경계

| 공유 상태 | 사례와 대응 |
| --- | --- |
| 테스트 클라이언트 | 기본 Authorization 헤더, 쿠키, 인터셉터의 변경이 다른 테스트로 남을 수 있다. 테스트마다 독립된 클라이언트를 쓰거나 요청마다 헤더를 명시한다. |
| 계정 단위 데이터 | 테스트마다 별도 계정을 사용하고 그 계정에 해당하는 결과만 조회한다. 각 테스트가 생성한 데이터 범위를 구분할 수 있다. |
| 전역 목록과 정렬 | 모든 계정의 데이터를 보는 API에서는 계정만 나눠도 결과가 섞인다. 테스트 전용 DB나 스키마, 테스트가 소유한 데이터 정리 등으로 전체 조회 범위를 통제한다. |
| 시간과 난수 | 시스템 시계와 임의 입력이 실패에 영향을 준다면 시각이나 입력을 고정하거나 재현 정보를 기록한다. |

Spring의 기본 singleton 빈은 컨테이너 안에서 재사용된다. 픽스처만 새로 만들고 내부 클라이언트를 공유하면 여전히 인증 상태가 전파될 수 있다. 픽스처와 가변 의존성의 수명을 함께 확인한다. 단독으로 통과하고 모음에서 실패한다면 실행 순서를 바꾸거나 병렬 실행을 비교해 공유 상태를 찾는다.

`@SpringBootTest(webEnvironment = RANDOM_PORT)`에서는 테스트 스레드와 HTTP 서버 스레드의 트랜잭션이 분리된다. 테스트 메서드의 `@Transactional` 롤백만으로 서버 요청에서 커밋한 데이터가 사라진다고 가정하면 테스트 간 간섭이 생긴다.
