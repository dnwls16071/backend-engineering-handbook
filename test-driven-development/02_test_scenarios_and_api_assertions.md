# Test Scenarios and API Assertions

테스트 시나리오는 대상, 사전 조건, 요청, 관찰 가능한 결과를 한 문장으로 연결한다. 테스트를 읽는 사람이 실패 메시지와 이름만 보고 어떤 약속이 깨졌는지 좁힐 수 있게 한다.

## 1. 시나리오를 실행 가능한 테스트로 바꾸기

- Arrange에서 시스템의 사전 상태와 이번 요청의 입력을 준비한다. 중복 요청을 검증하려면 같은 식별자의 기존 데이터가 먼저 있어야 한다.
- Act에서 검증할 호출을 한 번 수행한다. 준비 과정의 호출과 본검사를 구분한다.
- Assert에서 시나리오가 요구하는 결과를 확인한다. 성공 상태가 같아도 반환된 대상이나 저장된 값이 틀릴 수 있다.
- 같은 규칙과 기대 결과를 갖는 여러 입력은 `@ParameterizedTest`로 묶는다. 값이 단순하면 `@ValueSource`나 `@CsvSource`를, 복합 객체나 여러 인자가 필요하면 `@MethodSource`를 사용한다.
- 정상값, 누락, 형식 오류, 경계 바로 안과 밖 등 결과가 갈리는 입력을 고른다. 선택적 입력과 비어 있는 입력의 의미가 다르면 사례를 분리한다.

테스트 이름은 요구사항을 담고, 단언은 실패할 때 기대값과 실제값을 보여주도록 작성한다. 여러 구조를 검사하는 복잡한 조건은 이름 있는 헬퍼나 AssertJ의 `satisfies`로 표현할 수 있다. `matches` 같은 불리언 조건으로 묶을 때도 무엇이 틀렸는지 알 수 있도록 실패 메시지를 검토한다.

**공식 문서** [JUnit 매개변수화 테스트](https://docs.junit.org/5.14.4/writing-tests/parameterized-classes-and-tests.html) · [AssertJ 사용 가이드](https://assertj.github.io/doc/)

## 2. HTTP 계약과 접근 권한 검사

| 검증 대상 | 시나리오로 남길 내용 |
| --- | --- |
| 상태 코드 | 성공, 잘못된 요청, 인증 누락, 권한 부족, 대상 없음이 각각 계약에 맞게 응답한다. |
| 헤더 | 생성 응답의 `Location`, 인증 오류의 `WWW-Authenticate`, 본문이 있을 때의 `Content-Type`처럼 클라이언트가 사용하는 값을 검사한다. |
| 본문 | 요청한 리소스의 식별자와 필요한 속성이 일치한다. 오류라면 클라이언트가 사용하는 오류 형식과 필드를 검사한다. |
| 접근 제어 | 정상 권한, 인증 누락, 필요한 스코프 없음, 다른 계정이 소유한 리소스를 각각 준비해 기대한 결과를 확인한다. |

권한 부족을 403으로 알릴지, 리소스 존재를 감추기 위해 404 계약을 쓸지는 API의 정책에 맞춘다. 스코프 검사는 충분한 권한을 가진 사례와 부족한 사례를 짝지으면 실수로 모두 허용하거나 모두 거부하는 변경을 잡기 쉽다. JWT 서명이나 실제 필터의 동작을 검증한다면 가짜 인증 정보를 주입하는 테스트와 다른 범위가 필요하다.

상태 변경을 확인할 때는 이어지는 공개 조회에서 변경 결과를 검사할 수 있다. 예를 들어 생성 응답의 `Location`이 실제로 조회 가능한지 확인한다. 후속 조회가 필요한 테스트라면 준비에 쓰인 API의 실패도 즉시 드러나도록 한다.

**공식 문서** [HTTP 응답 의미와 상태 코드](https://www.rfc-editor.org/rfc/rfc9110.html) · [Spring Security OAuth 2.0 테스트](https://docs.spring.io/spring-security/reference/servlet/test/mockmvc/oauth2.html)

## 3. 목록과 페이지네이션에서 놓치기 쉬운 사례

| 질문 | 테스트에 넣을 예 |
| --- | --- |
| 포함 조건과 제외 조건이 작동하는가? | 조건을 만족하는 항목과 제외되어야 할 항목을 함께 준비한다. 빈 결과도 검사한다. |
| 응답 속성이 맞는가? | 식별자와 계약에 포함된 필드만 비교한다. 관련 엔터티의 정보가 필요하면 두 대상의 값이 각각 올바르게 매핑됐는지 본다. |
| 순서와 개수가 맞는가? | 정렬이 계약이면 `containsExactly` 또는 `containsExactlyElementsOf`로 순서, 개수, 요소를 확인한다. 순서가 자유로운 계약에는 순서 비의존 단언을 사용한다. |
| 페이지 경계가 맞는가? | 첫 페이지, 두 번째 페이지, 마지막 부분 페이지, 빈 결과를 검증한다. 이어지는 페이지에서 동일 항목이 중복되거나 빠지지 않는지 본다. |
| 동률을 어떻게 처리하는가? | 정렬 키가 같은 항목을 만들고 계약에 정의한 보조 정렬 키와 페이지 결과를 함께 검증한다. |

페이지 크기가 2이고 정렬된 데이터가 `[A, B, C, D, E]`라면 `[A, B]`, `[C, D]`, `[E]` 순서와 마지막 페이지 표시를 확인할 수 있다. 응답 형식이 목록 외에 전체 개수나 다음 페이지 정보를 약속한다면 본문 메타데이터도 단언한다.

## 4. 금액과 시간의 비교 기준

금액은 숫자 값만 중요한지, 소수 자릿수까지 계약인지 구분한다. `BigDecimal`의 `compareTo`는 `2.0`과 `2.00`을 숫자 값으로 같게 본다. `equals`는 스케일도 비교한다. 시간은 가능한 경우 고정된 시각을 준비하고, 실제 시각을 써야 하는 테스트에서는 요청 전후에 관측한 시각과 API가 보장하는 정밀도를 기준으로 범위를 검증한다.

**공식 문서** [JDK BigDecimal](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/math/BigDecimal.html) · [JDK Clock](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/time/Clock.html)
