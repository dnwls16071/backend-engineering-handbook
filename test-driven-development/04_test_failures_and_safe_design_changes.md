# Test Failures and Safe Design Changes

실패가 알려 주는 정보를 먼저 읽고, 깨진 것이 요구사항인지 테스트 준비 과정인지 구분한다. 공개 계약을 지키는 테스트를 바탕으로 내부 구조를 변경하고, 계약이 확장될 때는 새 시나리오를 먼저 만든다.

## 1. 예상하지 못한 실패 좁히기

| 실패 형태 | 확인 순서 |
| --- | --- |
| 컨텍스트가 시작되지 않음 | 최초 예외와 원인 예외를 확인한다. 빈 등록, 프로필, 테스트에서 불러온 설정 범위가 맞는지 본다. |
| 준비 호출이 실패함 | 응답을 읽기 전에 상태 코드와 응답 형식을 검사한다. 다른 테스트에서 쓰는 기본 데이터가 새 유효성 정책을 여전히 만족하는지 확인한다. |
| 기존 계약의 단언이 실패함 | 실패한 테스트부터 재실행하고 최근 변경을 확인한다. 기대값은 합의한 요구사항과 비교한다. |
| 모음에서만 간헐적으로 실패함 | 단독과 전체 실행을 비교한다. 순서, 병렬 실행, 시각, 난수, DB 상태를 기록하고 재현 조건을 한 가지씩 좁힌다. |

여러 테스트가 서로 다른 위치에서 가끔 실패한다면 최초 실패에서 공통으로 호출된 픽스처를 읽는다. 예를 들어 준비 단계에서 계정 생성이 400으로 거절된 뒤 토큰 응답을 읽으면, 표면의 예외는 null 접근이겠지만 실마리는 앞선 400이다. 준비 호출 자체에 실패 메시지를 두면 정책 변경 후 잘못된 기본값을 찾을 수 있다.

회귀가 발생한 변경을 모를 때는 통과하는 커밋과 실패하는 커밋을 확보한 뒤 `git bisect`로 범위를 좁힐 수 있다. 간헐적 실패는 반복 실행에서의 첫 실패 로그를 남기고 입력이나 환경을 고정한 작은 재현 사례로 바꾼다.

**공식 문서** [git bisect](https://git-scm.com/docs/git-bisect) · [Spring Boot 테스트 구성 찾기](https://docs.spring.io/spring-boot/reference/testing/spring-boot-applications.html#testing.spring-boot-applications.detecting-configuration)

## 2. 공개 동작을 유지하는 리팩터링

테스트가 통과하는 상태에서 변경할 책임을 하나 고른다. 테스트에서 관찰하는 결과와 오류 계약을 유지하며 이름 정리, 중복 제거, 내부 의존성 분리 같은 구조 변경을 적용한다. 관련 테스트를 실행해서 한 단계씩 확인한다.

HTTP로 관찰하기 어려운 요구사항은 더 가까운 경계에서 검증할 수 있다. 예를 들어 민감한 값이 평문으로 저장되지 않아야 한다면 저장 결과를 확인한다. 관찰할 조건을 최소화하면 저장 API의 세부 호출 순서나 특정 내부 클래스에 대한 의존을 줄일 수 있다.

CQRS처럼 명령과 조회의 책임을 분리할 때도 같은 방식으로 접근한다. 명령의 성공과 거절, 변경 이후 관찰 가능한 상태, 조회의 결과와 순서를 먼저 확보한다. 저장이나 조회 경로를 하나씩 교체하면서 공개 동작이 유지되는지 확인한다. 두 책임은 한 데이터베이스 안에서도 나눌 수 있다.

**참고** [Martin Fowler의 리팩터링 정의](https://martinfowler.com/bliki/DefinitionOfRefactoring.html) · [Martin Fowler의 CQRS 설명](https://martinfowler.com/bliki/CQRS.html)

## 3. 요구사항 변경에 따라 테스트 고치기

- 공개 계약이 그대로라면 기존 단언을 유지한다. 다른 내부 구현으로 바꿔도 소비자가 관찰할 수 있는 결과가 계속 맞는지 확인한다.
- 새 비즈니스 규칙이 추가되면 규칙이 갈리는 입력과 기대 결과를 시나리오로 먼저 적는다. 픽스처의 기본값이 더 이상 유효하지 않다면 기본값을 정리하고, 기존 테스트의 목적을 보존한다.
- 요청이나 응답 계약이 확장되면 바뀐 필드의 성공, 누락, 형식 오류와 하위 호환 범위를 확인한다. 새 필드가 여러 조회 응답으로 이어지면 영향을 받는 각 공개 응답을 시나리오에 포함한다.
- 같은 규칙을 반복 검사한다면 데이터 소스는 재사용할 수 있다. API마다 규칙이나 기대 결과가 달라졌다면 사례를 분리해 정책 차이가 보이게 한다.
