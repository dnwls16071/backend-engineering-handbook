# TDD Fundamentals and Feedback Loops

테스트 주도 개발은 요구사항을 검증 가능한 시나리오로 나누고, 한 번에 하나씩 실행 가능한 테스트로 옮겨 설계를 발전시키는 작업 방식이다. 새 동작이 생기는 순간에 기존 동작도 함께 확인할 수 있도록 피드백을 짧게 유지한다.

## 1. 첫 번째 클라이언트로서의 테스트

인터페이스 설계는 클라이언트가 시스템에 무엇을 요청하고 어떤 결과를 기대할 수 있는지 정하는 일이다. HTTP 요청과 응답, 모듈의 공개 메서드, 호출자가 받는 오류가 모두 여기에 해당한다. 구현 설계는 그 약속을 어떤 내부 구조로 충족할지 결정한다.

테스트를 첫 번째 클라이언트로 생각하면 인터페이스가 실제로 쓰기 쉬운지 일찍 확인할 수 있다. 예를 들어 생성 요청의 성공 조건을 표현하려면 호출에 필요한 정보와 클라이언트가 받는 결과부터 결정해야 한다. 응답을 관찰하는 테스트는 내부 메서드 호출 순서나 저장 방식이 바뀌어도 같은 계약을 검증할 수 있다.

설계의 출발점은 클라이언트가 얻을 결과다. 혼자 작업할 때는 첫 테스트를 쓰면서 인터페이스를 구체화하고, 다른 팀과 협업할 때는 시나리오를 정리하며 초안을 먼저 합의할 수 있다. 팀에서 확인이 필요한 계약과 나중에 바꾸기 쉬운 내부 결정을 구분하면 한 주기에 다룰 범위를 잡기 쉽다.

## 2. 시나리오 목록에서 Red → Green → Refactor로

| 단계 | 작업 | 확인할 것 |
| --- | --- | --- |
| 시나리오 목록 작성 | 클라이언트 관점에서 성공, 거절, 경계 조건을 적는다. | 항목마다 어떤 입력과 결과를 다룰지 설명할 수 있다. |
| Red | 한 항목을 테스트로 바꾸고 실행한다. | 예상한 이유로 실패한다. 예를 들어 응답이 404여야 하는데 200이 나온다. |
| Green | 새 테스트와 기존 테스트가 통과하도록 필요한 변경을 한다. | 변경 범위에 해당하는 기존 동작도 유지된다. |
| Refactor | 테스트가 통과하는 상태에서 이름, 중복, 책임을 다듬는다. | 관찰 가능한 동작은 유지되고 테스트가 계속 통과한다. |
| 반복 | 완료한 항목을 표시하고 새로 발견한 시나리오를 목록에 추가한다. | 다음 항목으로 넘어갈 때 확인할 동작이 분명하다. |

실패 원인이 한 번에 좁혀지지 않으면 보폭을 줄인다. 익숙한 변경이며 실패 원인을 바로 설명할 수 있다면 보폭을 조금 넓혀도 된다. 탐색 중에 누락된 요구사항을 발견하면 목록에 먼저 기록한 뒤 진행 중인 주기를 마친다. 구조를 손볼 필요가 있을 때 Refactor 단계를 활용한다.

## 3. 테스트 신호 해석하기

아래에서 양성은 테스트가 문제를 보고한 상태, 즉 실패를 뜻한다.

| 실제 동작 | 테스트 통과 | 테스트 실패 |
| --- | --- | --- |
| 요구사항을 충족함 | 정상 통과 | 거짓 양성. 테스트가 문제를 잘못 보고한다. |
| 요구사항을 위반함 | 거짓 음성. 테스트가 문제를 놓친다. | 정상 실패 |

- 예상보다 일찍 통과하면 입력이 의도한 분기에 도달했는지, 단언이 실제 결과를 읽는지 확인한다. 이미 성립하는 계약이라면 이후 회귀를 막을 가치가 있는지 판단하고, 필요하면 명시적인 회귀 테스트로 남긴다.
- 새 테스트가 실패하면 기대한 동작의 차이인지 확인한다. 빈 설정 누락, 픽스처 생성 오류, 연결 실패도 결과를 빨갛게 만들 수 있다.
- 테스트가 지나치게 약하면 기능이 깨져도 통과한다. 예를 들어 목록에 특정 요소가 있다는 단언만으로는 접근할 수 없는 요소가 함께 섞여 나오는 회귀를 잡기 어렵다.

## 4. 테스트 표면과 도구 선택

테스트 표면은 테스트가 시스템에 접근하는 공개 경계다. 비즈니스 규칙 자체의 피드백이 필요하면 공개 메서드 가까이에서 테스트한다. JSON 직렬화, HTTP 상태 코드, 보안 필터, 저장 계층의 상호작용이 요구사항이면 그 동작이 포함된 경계에서 확인한다. 범위가 넓을수록 더 많은 연결을 검증하고, 범위가 좁을수록 실패 지점을 빨리 찾기 쉽다.

테스트 대역, Java 인터페이스, 특정 아키텍처는 비용을 줄일 필요가 있을 때 선택한다. 예를 들어 실제 DB 엔진의 제약이나 쿼리 동작이 중요하면 해당 엔진으로 테스트하는 편이 검증 목적에 맞다. 외부 서비스가 느리거나 제어하기 어렵다면 대역을 사용하되, 실제 연동 계약은 알맞은 범위에서 확인한다.

생성형 AI는 반복적인 테스트 틀과 데이터 후보를 만드는 데 쓸 수 있다. 어떤 사례가 요구사항을 대표하는지, 예상한 이유로 Red가 발생하는지, 단언이 실제 실패를 잡는지는 작성자가 확인한다.
