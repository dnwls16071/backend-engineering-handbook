# 병목 해소와 성능 개선을 위한 시스템 확장

## 1. 성능과 가용성을 함께 고려한다

- **시스템을 확장할 때는 Throughput과 Latency뿐 아니라 장애나 작업 중에도 서비스를 제공할 수 있는 가용성을 함께 고려한다.**
- 가용성(Availability)은 시스템이 정상적으로 서비스를 제공할 수 있는 정도이다.
- 시간 기준으로는 약속한 서비스 제공 시간 중 정상적으로 이용할 수 있었던 시간의 비율로 표현한다.

```text
가용성 = 정상 서비스 제공 시간 / 전체 서비스 제공 예정 시간 × 100
```

- 365일 내내 운영하는 서비스에서 가용성 99.99%에 해당하는 중단 시간은 연간 약 53분이다. 실제로 매년 그만큼 중단된다는 뜻은 아니다.
- 장애 발생 가능성을 줄이고, 장애가 발생했을 때 복구 시간을 짧게 만들어 서비스 중단 시간을 줄인다.
- 서버 한 대의 성능을 높이는 것과 장애 중에도 서비스를 유지하는 것은 구분해서 설계한다.

## 2. 시스템 이중화로 일부 장애에 대응한다

- 시스템 이중화는 일부 구성요소를 사용할 수 없어도 다른 구성요소를 통해 서비스를 계속 제공할 수 있게 만드는 방식이다.
- 도시를 연결하는 도로가 두 개라면 한 도로에 사고가 나거나 공사를 하더라도 다른 도로를 이용할 수 있다.
- 애플리케이션 서버를 여러 대로 구성하면 한 서버의 장애나 배포 중에 다른 서버가 요청을 처리하도록 만들 수 있다.
- **서버 수를 늘리는 것만으로 가용성이 보장되지는 않는다. 장애 감지와 요청 전환이 함께 동작해야 한다.**
- 남은 서버가 필요한 부하를 감당할 수 있는지, DB나 로드밸런서 등에 단일 장애 지점이 남아 있는지도 확인한다.

## 3. 수평적 확장과 수직적 확장을 비교한다

| 구분 | 수평적 확장(Scale-out) | 수직적 확장(Scale-up) |
| :--- | :--- | :--- |
| 방식 | 같은 역할의 서버 수를 늘린다. | 서버의 CPU, 메모리 등 자원 사양을 높인다. |
| 장점 | 요청을 여러 서버로 나누고 일부 서버 장애에 대응할 수 있다. | 서버 간 요청 분산을 추가하지 않고 처리 자원을 늘릴 수 있다. |
| 필요한 작업 | 로드밸런싱, 상태 공유와 여러 서버의 운영을 고려한다. | 사양 변경 방식, 재시작과 작업 중 서비스 제공 방법을 확인한다. |
| 한계 | 공유 DB, 상태 관리와 분산 처리 비용이 확장을 제한할 수 있다. | 선택 가능한 사양과 단일 서버의 처리 능력에 한계가 있다. |
| 가용성 | 장애 감지와 전환을 구성하면 가용성을 높일 수 있다. | 확장 자체로 이중화가 되지는 않으며, 재시작이 필요하면 중단이 발생할 수 있다. |

- 수평적 확장도 무제한으로 성능을 높이지는 못한다. 서버를 늘린 뒤 공유 자원에 병목이 생기는지 확인한다.
- 수직적 확장이 항상 다운타임을 요구하는 것은 아니다. 서비스와 변경 방식에 따라 중단 여부가 달라진다.
- 현재 병목과 운영 복잡도, 비용을 비교해 방식을 선택하며 두 방식을 함께 적용할 수도 있다.

## 4. 캐싱으로 반복 조회 비용을 줄인다

- 캐싱(Caching)은 데이터를 더 빠르게 조회할 수 있는 곳에 임시로 저장해 재사용하는 방식이다.
- 자주 조회하는 데이터를 Redis 같은 메모리 기반 캐시에 저장하면 DB로 전달되는 조회 요청을 줄일 수 있다.
- 정적 파일을 CDN에 캐싱하면 사용자와 가까운 위치에서 응답하고 원본 서버의 전송 부하를 줄일 수 있다.

| 적용 대상 | 기대 효과 | 함께 고려할 내용 |
| :--- | :--- | :--- |
| 정적 파일 CDN | 전송 지연과 원본 서버의 트래픽을 줄인다. | 파일 변경 시 갱신과 캐시 무효화 방법을 정한다. |
| DB 조회 결과 캐시 | 반복 조회의 응답 시간을 줄이고 DB 부하를 낮춘다. | 만료 시간, 데이터 변경 시 갱신과 허용 가능한 오래된 데이터의 범위를 정한다. |

- **캐싱은 재사용할 수 있는 요청의 처리 비용을 줄이는 전략이다. 데이터 최신성과 갱신 비용을 함께 판단한다.**
- 캐시에 데이터가 없으면 DB나 원본 서버에서 조회해야 한다. 캐시 미스가 늘거나 캐시를 사용할 수 없을 때 원본에 몰리는 부하도 확인한다.

## 5. 트래픽 증가에 맞춰 필요한 구성을 추가한다

| 구성 변화 | 해결하려는 문제 | 적용 방법 |
| :--- | :--- | :--- |
| 단일 서버로 시작 | 초기 관리와 구성 비용을 줄인다. | 프론트엔드, 백엔드와 DB를 한 서버에서 실행한다. |
| DB 분리 | DB와 웹 애플리케이션의 CPU, 메모리와 디스크 경합을 줄인다. | 웹 애플리케이션과 DB를 별도 서버로 구성한다. |
| 정적 파일 처리 분리 | 큰 파일의 저장과 전송이 애플리케이션 처리에 미치는 영향을 줄인다. | 이미지·동영상 등의 정적 파일을 S3 같은 저장소로 분리한다. |
| CDN 도입 | 정적 파일의 전송 지연과 원본 접근을 줄인다. | CloudFront 같은 CDN을 통해 파일을 캐싱하고 전달한다. |
| 애플리케이션 서버 확장 | 서버 한 대의 처리 능력 한계를 해소하고 장애 대응 여지를 확보한다. | 서버를 여러 대로 늘리고 로드밸런서로 요청을 분산한다. |
| DB 성능 개선 | 늘어난 애플리케이션 요청으로 발생한 DB 병목을 줄인다. | 쿼리와 인덱스를 개선하고 필요하면 DB 사양을 높인다. |
| 읽기 전용 DB 도입 | 조회 부하를 여러 DB로 나눈다. | 읽기 복제본(Read Replica)으로 분리 가능한 조회를 전달한다. |
| 캐시 서버 도입 | 반복 조회에 따른 DB 부하와 응답 시간을 줄인다. | 자주 조회하는 데이터를 캐싱한다. |

- 이 순서는 모든 서비스가 따라야 하는 고정 절차가 아니다. 부하 테스트에서 확인한 병목과 요구사항에 따라 필요한 구성을 선택한다.
- 정적 파일 분리와 CDN은 애플리케이션 로직의 계산 비용이나 DB 쿼리 비용을 직접 줄이지 않는다.
- 애플리케이션 서버를 늘리면 DB에 도달하는 요청도 증가할 수 있으므로 확장 후 전체 요청 경로를 다시 확인한다.

## 6. DB 확장은 조회 특성과 데이터 동기화를 함께 본다

- DB가 병목이면 먼저 비효율적인 쿼리, 인덱스와 불필요한 데이터 접근을 확인한다.
- 역정규화는 조회 비용을 낮출 수 있지만 데이터 중복과 갱신 시 정합성 관리 비용이 늘어날 수 있다.
- 수직적 확장은 DB 구조를 크게 바꾸지 않고 자원을 늘릴 수 있지만 사양과 비용에 한계가 있다.
- DB의 수평적 확장에는 복제나 샤딩 같은 방식이 있으며 데이터 배치, 동기화와 쿼리 처리의 복잡도를 함께 고려한다.

### 읽기 복제본으로 조회 부하를 분산한다

- 주 DB가 쓰기를 처리하고 읽기 복제본이 조회의 일부를 처리하도록 나눌 수 있다.
- 복제본의 데이터 반영이 늦어지면 최신 쓰기 결과가 즉시 조회되지 않을 수 있다.
- 최신성이 필요한 조회와 지연을 허용할 수 있는 조회를 구분하고, 각각 어느 DB로 보낼지 정한다.
- **읽기 복제본은 조회 부하를 분산하는 수단이며 주 DB의 쓰기 처리 한계를 직접 해소하지는 않는다.**
- 캐싱과 읽기 복제본 중 어느 방식이 적합한지는 조회 패턴, 최신성 요구와 운영 비용을 비교해 결정한다.

## 7. 병목 위치에 맞는 개선 방법을 선택한다

| 병목 위치 | 우선 확인할 내용 | 개선 후보 |
| :--- | :--- | :--- |
| 웹 애플리케이션 서버 | 비효율적인 로직, 정적 파일 처리와 요청 집중을 확인한다. | 로직 개선, 정적 파일 분리, 로드밸런서를 이용한 수평적 확장과 수직적 확장이다. |
| DB 서버 | 비효율적인 쿼리, 조회량과 자원 부족을 확인한다. | SQL·인덱스 개선, 수직적 확장, 읽기 복제본과 캐시 도입이다. |

- 병목이 아닌 구간을 확장해도 전체 처리량이 늘지 않을 수 있다.
- 개선 전후의 부하와 데이터 조건을 맞추고 Throughput, Latency와 자원 사용을 비교한다.
- 성능이 개선되었는지뿐 아니라 장애 전환, 데이터 최신성과 운영 비용이 요구사항을 만족하는지도 확인한다.
- 목표 달성 여부와 새로 생긴 병목을 확인한 뒤 다음 개선 대상을 정한다.
