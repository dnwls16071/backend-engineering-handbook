# 부하 테스트로 병목 지점 파악하기

## 1. 병목 지점은 전체 시스템의 처리 능력을 제한한다

- **병목 지점(Bottleneck Point)은 특정 자원이나 구성요소의 처리 능력이 한계에 도달해 전체 시스템의 성능을 제한하는 구간이다.**
- 고속도로가 3차선에서 2차선으로 좁아지면 차량이 몰리고 정체가 발생한다. 시스템에서도 요청이 특정 구간의 처리 능력을 넘으면 대기가 늘어난다.
- 정체가 없는 도로를 넓혀도 좁아진 구간의 처리 능력은 늘어나지 않는다. 성능 개선도 현재 처리 능력을 제한하는 지점을 찾아 진행한다.

### 병목 구간이 전체 처리량을 결정한다

- 모든 요청이 백엔드와 DB를 순서대로 거치며, 요청 하나가 각 구간에서 같은 단위의 작업 하나를 수행한다고 가정한다.

| 구성요소 | 초당 처리 가능한 요청 수 | 전체 처리량에 미치는 영향 |
| :--- | :--- | :--- |
| 백엔드 서버 | 1,000개 | DB의 처리 능력보다 여유가 있다. |
| DB | 300개 | 전체 시스템의 처리량을 초당 300개로 제한한다. |

- 이 조건에서는 백엔드만 확장해도 전체 처리량은 늘어나지 않는다.
- DB를 개선해 초당 1,500개를 처리할 수 있게 만들면 전체 처리량은 백엔드의 한계인 초당 1,000개가 된다.
- **한 병목을 해소하면 다른 구간이 새로운 병목이 될 수 있으므로 개선 후 다시 측정한다.**

## 2. 목표 설정부터 개선 검증까지 반복한다

| 단계 | 수행할 내용 |
| :--- | :--- |
| 테스트 필요성 확인 | 서비스 출시나 이벤트 전에 예상 트래픽을 감당할 수 있는지 확인한다. |
| 목표 설정 | 예상 요청량을 바탕으로 목표 Throughput을 정하고, 서비스 특성에 맞는 Latency 목표를 정한다. |
| 현재 성능 측정 | k6 등의 도구로 부하를 점차 높이며 처리량과 응답 시간의 변화를 측정한다. |
| 병목 진단과 개선 | 같은 시간대의 자원 사용과 요청 처리 상태를 확인해 성능을 제한하는 지점을 개선한다. |
| 재측정 | 개선 전후의 결과를 비교하고 목표 달성 여부와 새로운 병목을 확인한다. |

- 목표의 예로 처리량 2,000 TPS, 평균 응답 시간 800ms를 정할 수 있다. 실제 목표는 예상 트래픽과 사용자 경험에 맞춰 정한다.
- 동시 사용자 수가 곧 초당 요청 수는 아니다. 사용자당 요청 빈도와 행동을 고려해 부하를 구성한다.
- 최대 처리량뿐 아니라 목표 응답 시간을 유지할 수 있는 처리량도 확인한다.
- 목표에 미치지 못하면 병목 진단, 개선과 재측정을 반복한다.

## 3. 테스트 시간과 데이터, 실행 환경을 맞춘다

| 준비 항목 | 확인할 내용 | 이유 |
| :--- | :--- | :--- |
| 테스트 시간 | 모니터링 수집 주기를 고려해 충분한 관측 구간을 확보한다. | 테스트가 너무 짧으면 일시적인 변화나 적은 표본만 보고 판단할 수 있다. |
| 데이터 규모와 구성 | 운영과 비슷한 데이터 양, 분포와 저장 상태를 준비한다. | DB 성능은 데이터의 양과 구성에 따라 달라진다. |
| 실행 환경 | 운영 서비스와 분리된 환경에서 테스트한다. | 테스트 부하가 실제 사용자 요청의 처리에 영향을 줄 수 있다. |

- 모니터링 값이 1분 간격으로 기록된다면 최소 5분 이상 테스트해 여러 관측값을 확보한다. 안정 상태 확인과 테스트 목적에 따라 더 긴 시간이 필요할 수 있다.
- 데이터가 거의 없는 DB에서 얻은 결과를 운영 규모의 성능으로 판단하지 않는다.
- 운영과 유사한 테스트 데이터를 구성하거나 DB 복제본을 활용해 데이터 준비 시간을 줄일 수 있다.
- 개선 전후에는 부하, 데이터와 환경 조건을 맞춰야 변경 효과를 비교할 수 있다.

## 4. 모니터링으로 자원 상태를 지속해서 확인한다

- **모니터링(Monitoring)은 대상의 상태를 지속적으로 관찰하는 활동이며, 메트릭(Metric)은 그 상태를 나타내는 수치나 측정값이다.**
- CPU 사용률, 메모리 사용률, 초당 요청 수와 응답 시간은 모두 메트릭이다.
- 부하 테스트 결과만으로는 어느 구성요소가 성능을 제한하는지 알기 어렵다. 백엔드, DB, 캐시와 로드밸런서 등 요청 경로의 상태를 함께 확인한다.
- 자원 사용률과 처리량, 응답 시간을 같은 시간대에 비교하면 부하 증가에 따른 변화를 파악하기 쉽다.
- 관리형 서비스는 제공되는 지표와 관측 범위가 다를 수 있으므로 확인 가능한 메트릭을 선택한다.

### 사용률만으로 병목을 확정하지 않는다

- 높은 자원 사용률은 병목의 단서이다. 처리량 정체와 응답 지연이 함께 나타나는지 확인한다.
- 사용률이 100%가 되기 전에도 자원 경합과 대기로 성능이 나빠질 수 있다.
- CPU와 메모리에 여유가 있어도 연결 풀 고갈, 잠금 대기나 외부 서비스 지연으로 요청이 밀릴 수 있다.
- **사용률이 높다는 사실과 실제로 전체 성능을 제한한다는 판단을 구분한다.**

## 5. CPU, 메모리와 디스크의 역할을 구분한다

| 자원 | 역할 | 사용이 늘어나는 작업의 예 |
| :--- | :--- | :--- |
| CPU | 명령어를 실행하고 연산을 수행한다. | 반복 계산, 요청 처리, 인코딩·디코딩과 암호화이다. |
| 메모리(Memory, RAM) | 실행 중인 코드와 데이터, 작업에 필요한 임시 상태를 보관한다. | 큰 배열 생성, 많은 조회 결과 유지와 캐시 데이터 저장이다. |
| 디스크(Disk) | 파일과 데이터를 지속적으로 저장한다. | DB 데이터 읽기·쓰기, 파일 처리와 로그 기록이다. |

- 메모리는 일반적으로 디스크보다 데이터 접근이 빠르다. 프로그램은 필요한 데이터를 메모리에 올려 처리한다.
- 단순 계산을 계속 반복하면 CPU 사용이 늘고, 큰 데이터를 메모리에 할당하고 유지하면 메모리 사용이 늘어난다.
- 하나의 작업이 여러 자원을 함께 사용한다. 큰 배열 생성도 메모리 할당뿐 아니라 반복 연산에 CPU를 사용한다.
- 디스크 저장 공간의 부족과 디스크 읽기·쓰기 성능의 한계는 구분한다.

## 6. 구성요소별 작업 특성으로 원인 후보를 좁힌다

| 구성요소 | 대표적인 자원 사용 | 확인할 내용 |
| :--- | :--- | :--- |
| DB | 디스크에서 데이터를 읽고 메모리에 유지하며 CPU로 필터링·정렬·집계한다. | 조회 데이터 양, 쿼리 연산, 메모리와 디스크 접근을 함께 확인한다. |
| 백엔드 서버 | CPU로 요청과 업무 로직을 처리하고 메모리에 객체와 조회 결과를 유지한다. | 복잡한 연산, 큰 조회 결과, 동시 요청에 따른 메모리 증가를 확인한다. |
| 로드밸런서 | 연결과 요청을 관리하고 트래픽을 백엔드로 전달한다. | 요청량, 연결 상태와 트래픽 처리 한계를 확인한다. |
| 캐시(Redis) | 메모리에 데이터를 유지하고 CPU로 명령을 실행한다. | 데이터 크기와 메모리 여유, 명령 실행 비용을 함께 확인한다. |

- 자원 사용은 구성요소의 이름만으로 결정되지 않는다. 실제 로직, 데이터 크기와 설정에 따라 달라진다.
- 백엔드는 파일 처리나 로그 기록에서 디스크를 사용하고, Redis도 영속화 설정에 따라 디스크를 사용할 수 있다.
- CPU와 메모리를 우선 확인하되, 원인이 설명되지 않으면 Disk I/O와 Network I/O까지 범위를 넓힌다.
- Disk I/O는 디스크 읽기·쓰기 작업이며, Network I/O는 네트워크를 통한 데이터 송수신 작업이다.

## 7. 측정 결과를 개선 판단으로 연결한다

- 부하를 높일 때 처리량이 더 늘지 않는 구간과 응답 시간이 증가하는 시점을 확인한다.
- 같은 시점의 구성요소별 자원 사용과 대기 상태를 비교해 병목 후보를 찾는다.
- 후보 지점이 어떤 요청이나 작업을 제한하는지 확인하고 개선한다.
- 같은 조건으로 다시 테스트해 처리량과 응답 시간이 실제로 나아졌는지 검증한다.
- 목표 달성 여부와 새로운 병목을 확인한 뒤 다음 개선 대상을 정한다.
