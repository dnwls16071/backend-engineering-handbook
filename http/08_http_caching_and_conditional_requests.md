# HTTP Caching and Conditional Requests

HTTP 캐시는 저장해 둔 응답을 재사용해 전송량과 응답 시간을 줄인다. 신선한 응답은 조건에 맞으면 바로 사용할 수 있다. 신선도가 지난 응답은 조건부 요청으로 변경 여부를 확인할 수 있다.

## 1. 저장과 신선도

브라우저 캐시는 특정 사용자 에이전트의 응답을 보관하는 사설 캐시다. CDN이나 캐싱 프록시는 여러 요청자에게 응답을 재사용할 수 있는 공유 캐시다. 캐시가 보통 사용하는 키는 요청 메서드와 URI이며, `Vary`가 지정한 요청 헤더 값도 응답 선택에 사용한다.

| 상태 | 다음 요청에서 하는 일 |
| --- | --- |
| 저장된 응답이 없음 | 서버에 요청한다. 저장 조건을 충족하면 받은 응답을 보관한다. |
| 저장된 응답이 신선함 | 캐시 키가 일치하고 재검증을 요구하는 지시어가 없다면 응답을 재사용할 수 있다. |
| 저장된 응답의 신선도가 지남 | 검증자가 있으면 조건부 요청을 보낸다. 검증자가 없으면 일반 요청으로 새 응답을 받아야 할 수 있다. |

`Cache-Control: max-age=60`은 응답의 신선도 수명을 60초로 정한다. `Age`는 원 서버가 그 응답을 생성하거나 마지막으로 검증한 이후 경과한 시간의 추정값이며, 캐시에서 보낸 시간과 전달 지연 등이 반영될 수 있다.

## 2. 검증자와 조건부 요청

| 응답의 검증자 | 후속 요청의 조건 | 특징 |
| --- | --- | --- |
| `ETag` | `If-None-Match` | 서버가 부여한 불투명한 표현 태그를 비교한다. 해시나 버전 식별자 등을 태그 생성에 사용할 수 있다. |
| `Last-Modified` | `If-Modified-Since` | 마지막 수정 날짜와 시각을 비교한다. 초 단위 시각만으로는 같은 초에 발생한 변경을 구별하기 어려울 수 있다. |

둘 다 있으면 `If-None-Match`를 먼저 평가하고 `If-Modified-Since`는 무시한다. 조건부 `GET` 또는 `HEAD`에서 저장한 표현이 여전히 유효하면 서버가 콘텐츠 없이 `304 Not Modified`를 반환한다. 캐시는 저장된 메타데이터를 갱신하고 기존 콘텐츠를 재사용한다. 표현이 바뀌었다면 일반적인 전체 `GET` 요청과 같은 방식으로 새 표현을 반환할 수 있다.

예를 들어 `ETag: "menu-v3"`와 `Cache-Control: max-age=60`으로 저장한 메뉴가 만료되면 다음과 같이 확인한다.

```http
GET /menu.json HTTP/1.1
Host: example.com
If-None-Match: "menu-v3"

```

변경되지 않은 경우

```http
HTTP/1.1 304 Not Modified
Date: Fri, 20 Nov 2026 00:01:30 GMT
ETag: "menu-v3"
Cache-Control: max-age=60

```

## 3. Cache-Control 지시어

| 응답 지시어 | 캐시 동작 |
| --- | --- |
| `max-age=N` | 응답의 신선도 수명을 N초로 설정한다. |
| `s-maxage=N` | 공유 캐시에서 `max-age`나 `Expires`를 대신한다. 공유 캐시는 신선도가 지난 응답을 재검증 없이 재사용할 수 없다. |
| `public` | 일반적인 저장 조건에서 제한되는 경우에도 공유 캐시에 저장할 수 있음을 명시한다. |
| `private` | 응답을 특정 사용자용으로 지정해 공유 캐시의 저장을 막는다. |
| `no-cache` | 저장은 가능하며, 다시 쓰기 전에 성공적인 검증이 필요하다. |
| `no-store` | 해당 응답의 저장과 재사용을 금지한다. |
| `must-revalidate` | 신선한 동안은 재사용할 수 있다. 신선도가 지난 뒤에는 성공적인 검증이 필요하며, 연결이 끊겼으면 오류를 반환한다. |

`Expires`는 절대 만료 시각을 표현한다. 적용되는 `max-age`나 `s-maxage`가 있으면 해당 지시어가 우선한다. `Pragma: no-cache`는 오래된 HTTP/1.0 요청과의 호환을 위한 필드로, 응답의 캐시 정책은 `Cache-Control`에 명시한다.

## 4. 정책 선택과 무효화

- 사용자별 대시보드는 `private, no-cache`로 브라우저에 저장을 허용하면서 매번 재사용 전에 검증하도록 할 수 있다.
- 토큰이나 일회용 비밀번호처럼 저장을 막아야 하는 응답에는 `no-store`를 쓸 수 있다.
- 공개 메뉴를 CDN과 브라우저에서 서로 다른 기간 동안 유지하려면 `public, max-age=60, s-maxage=300`처럼 지정할 수 있다.

`no-store`는 해당 응답의 저장 정책이다. 이전 응답의 재사용을 피하려면 업데이트된 자원을 새 URI에 배치하거나 CDN의 purge 기능으로 저장 항목을 제거할 수 있다. 캐시는 `PUT`, `POST`, `DELETE`처럼 안전하지 않은 메서드의 요청을 전달하고 `2xx`나 `3xx` 응답을 받으면 대상 URI의 저장 응답을 무효화한다. 다른 캐시에서도 무효화되는지는 해당 요청이 통과한 경로에 달려 있다.
