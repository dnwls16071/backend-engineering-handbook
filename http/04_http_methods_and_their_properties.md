# HTTP Methods and Their Properties

HTTP 메서드는 대상 자원에 어떤 동작을 요청하는지 나타낸다. 예를 들어 `/tasks/42`는 특정 작업을 식별한다. 동일한 URI에 `GET`을 보내면 작업을 읽고, `PATCH`를 보내면 요청에 명시한 부분을 변경할 수 있다.

## 1. 자원을 먼저 식별하기

| 요청 | 의미 |
| --- | --- |
| `GET /tasks` | 작업 목록의 표현을 조회한다. |
| `GET /tasks/42` | 특정 작업의 표현을 조회한다. |
| `POST /tasks` | 컬렉션이 전달받은 데이터를 처리한다. 작업 생성은 가능한 처리의 한 예다. |
| `PUT /tasks/42` | 요청 콘텐츠로 해당 URI의 상태를 만들거나 교체한다. |
| `PATCH /tasks/42` | 요청 콘텐츠가 기술한 변경을 해당 자원에 적용한다. |
| `DELETE /tasks/42` | 대상 URI와 현재 연결된 기능의 제거를 요청한다. 실제 저장 데이터의 폐기는 서비스 정책에 달려 있다. |

`GET` 요청 본문의 의미는 표준에서 일반적으로 정의하지 않는다. 조회 조건은 보통 쿼리로 보낸다. `PUT`은 대상 상태 전체를 뜻하는 표현을 제출할 때 적합하므로, 일부 필드만 보내는 갱신은 계약에 따라 `PATCH`와 해당 패치 문서의 미디어 타입을 사용한다.

`HEAD`는 `GET`과 같은 의미로 메타데이터를 요청하되 응답 콘텐츠는 받지 않는다. `OPTIONS`는 대상의 통신 옵션을 묻고, `CONNECT`는 터널을 요청하며, `TRACE`는 요청 경로의 진단용 루프백을 요청한다.

## 2. 안전성과 멱등성

| 메서드 | 안전 | 멱등 | 응답 캐시 |
| --- | --- | --- | --- |
| `GET` | 예 | 예 | 가능 |
| `HEAD` | 예 | 예 | 가능 |
| `POST` | 아니요 | 기본적으로 아니요 | 명시적 신선도와 요청 URI에 맞는 `Content-Location` 등 조건 충족 시 가능 |
| `PUT` | 아니요 | 예 | 불가 |
| `PATCH` | 아니요 | 기본적으로 아니요 | 명시적 신선도와 요청 URI에 맞는 `Content-Location` 등 조건 충족 시 가능 |
| `DELETE` | 아니요 | 예 | 불가 |

안전한 메서드는 클라이언트가 서버 상태의 변경을 요청하지 않는 메서드다. 조회를 처리하면서 접근 로그를 남길 수 있다. 멱등성은 동일한 요청을 반복했을 때 서버에 의도한 효과가 한 번 요청한 것과 같다는 뜻이다. 예를 들어 첫 `DELETE`는 `204`, 다음 `DELETE`는 `404`를 반환해도 대상이 제거된 상태는 같다. 조건을 충족해 저장한 `POST`와 `PATCH` 응답은 후속 `GET`이나 `HEAD`에 재사용할 수 있다.

## 3. 재시도와 동시 변경

통신이 끊겨 첫 요청의 성공 여부를 모를 때 멱등 메서드는 같은 요청을 다시 시도하기 수월하다. 결제 생성처럼 `POST`가 중복 실행되면 문제가 되는 작업은 API가 지원하는 중복 제거 규칙을 확인해야 한다. 한 자원을 여러 사용자가 수정하는 경우에는 `ETag`와 `If-Match`를 사용해 읽은 버전이 여전히 최신일 때만 수정하도록 할 수 있다.

HTML 폼과 생성 API에서 메서드를 선택하는 예시는 [05번 문서](05_http_request_data_and_api_design.md)에서 다룬다.
